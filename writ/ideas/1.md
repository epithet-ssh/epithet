# Writ, NADIR, and Epithet Ecosystem — Design Notes

Captured from a design conversation. These are working notes, not commitments —
the point is to have the shape of the decisions written down so you can return
to them when building.

## Project scope and naming

### Writ — sophisticated policy server

Writ is a separate project from epithet, not a subcommand or mode. The case
for separation:

- It's stateful (needs a database, probably Postgres)
- Different deployment story than stateless epithet policy — backup/restore,
  schema migrations, replication concerns
- Different dependencies that epithet users shouldn't have to carry if they
  don't need writ
- Different operational skill set to run
- Complementary rather than alternative — a shop might run plain epithet for
  dev/CI and writ for production

### Key architectural difference from built-in epithet policy

- **Epithet built-in policy**: principal == username. A given cert tends to
  work on multiple hosts.
- **Writ**: principal is a unique `{remote-user, host}` tuple. A cert is
  issued for access as a single user on a single host.

The narrow principal model is what unlocks the sophisticated policy decisions
writ is designed for: workflow-based external approval, oncall checks, etc.

### Relationship between writ and epithet

- Writ is a policy server that speaks epithet's policy protocol
- Same wire format, same cert semantics; different backend
- Epithet's CA can point at writ the same way it points at the built-in
  simple policy server
- Positioning: "writ is the next step up when you outgrow epithet's simple
  policy" rather than "writ and epithet are alternatives you must choose
  between"
- This means epithet's policy protocol becomes a first-class, documented,
  public interface — not an internal detail. Worth treating as such now.

### Naming philosophy for the ecosystem

One evocative/distinctive name is the budget for an OSS infrastructure
project. Epithet has already spent that budget. Writ, as a separate project,
gets its own budget (and spends it on "writ"). Everything else should be
descriptive English.

Rationale: every evocative name is a concept users have to learn before they
can reason about the system. Naming tax is small per encounter but paid
constantly. Components that operators touch most (logs, config, deployment)
benefit most from descriptive names.

### Writ's future component lineup (sketch)

Descriptive names within writ's own namespace:

- `writ server` — the policy server itself
- `writ host-agent` (or `writ sentinel`) — per-host agent that reports local
  users/accounts and keeps writ's view current
- `writ scim` — SCIM provisioner for user identity sync
- `writ bastion` — bastion for session mediation, immediate session
  termination
- NADIR client for host cert provisioning (see below — NADIR is independent)

### Scots Gaelic options explored and shelved

Considered and set aside in favor of "writ":

- `breith` (judgment/decision) — good candidate, domain `breith.org`
  available
- `beachd` (opinion/view)
- `ainmichte` (the named/specified one)
- `iomradh` (mention/reference)

blog, vanity redirects.

## Implementation order for writ

1. **First step**: get to `{host, user}` pairings for principals so narrow
   certificates can start being issued.
2. **Support dynamic hosts and remote users**: mechanism likely a cron job on
   the host that checks for new local accounts, configures principals for
   them, reports back to the policy server with what it configured.
3. **Later**: dynamic users for epithet itself (not host users/remote users),
   probably via a SCIM API implementation. Lot of thought and detail still
   needed here.

## NADIR — ACME-like protocol for SSH host certificates

### Motivation

ACME solved TLS cert automation by defining a standardized protocol any CA
and any client could implement. For SSH host certs, the equivalent gap
exists: step-ca, Vault, Teleport, and others each have their own cert
issuance flows, but there's no standardized protocol that interoperates
across CAs. NADIR fills that gap.

### Scope decisions

- **Independent project**, not a writ feature. Writ (and others) would
  implement NADIR.
- **Host certs only in v1.** Maybe extension points for user certs later, but
  user cert enrollment has fundamentally different attestation needs and
  should not drive the v1 design.
- **Spec is the primary deliverable**, not code. Follow the ACME/RFC 8555
  model: a document clear enough that independent implementations can
  interop.

### Positioning

Tagline: **NADIR is ACME for SSH.** Mirror ACME's protocol structure (new-
order, authorizations, challenges, finalize) so the mental model carries
over.

### Name

NADIR = backronym, to be finalized. Working options:

- Node Attestation & Delegated Identity Renewal
- Network Attestation and Delegated Identity Renewal
- Node Attestation and Delegated Issuance Renewal

Pairs aesthetically with ACME (acme = summit, nadir = lowest point;
ACME/TLS = application layer, NADIR/SSH = foundational infrastructure).

### Challenge type: ssh-callback-01 (working name)

The initial challenge type for v1. DNS-name-based trust, equivalent to
Let's Encrypt's HTTP-01 in spirit.

**Flow:**

1. Host generates (or already has) SSH host keypair.
2. Host creates an enrollment request (the CSR) containing:
   - Claimed hostname(s)
   - Host public key
   - SSH port (default 22)
   - CA identifier (so a signed request for one CA can't be submitted to
     another)
   - Nonce from CA or timestamp (to prevent replay)
   - Signature over the above using host private key (using `sshsig` format
     from PROTOCOL.sshsig — widely supported, used for git commit signing)
3. Host POSTs the request to the CA's NADIR endpoint over TLS.
4. CA verifies the request signature against the claimed public key. This
   proves the requester holds the host private key.
5. CA connects to each claimed hostname on SSH.
6. CA observes the server host key from the SSH handshake (RFC 4253 §7 key
   exchange — server's host key plus signature over exchange hash proves
   possession of the corresponding private key).
7. CA verifies observed host key matches the claimed key in the request.
8. If all match: CA issues cert, returns via response channel.

**What this proves:** the requester has the host key, AND the host key is
the one currently answering SSH at the claimed name. Same trust model as
early Let's Encrypt — network-level name control.

**What it doesn't prove:** that the machine is "the right" machine in any
deeper sense. If an attacker controls DNS/routing for the name at
verification time, they can pass the challenge. This is acceptable for v1;
ACME has the same property. Attestation-based challenge types (TPM, cloud
metadata, mTLS with existing PKI) can be added later as additional challenge
types.

**Renewal flow:** much simpler. Host presents current cert via mTLS to CA;
if cert is valid and not near expiry, CA issues a new one. No callback
needed.

### Design notes and open questions

- **Account keys vs. host keys.** ACME has account keypair (authenticates
  API calls) distinct from cert subject keypair. For NADIR v1, these can
  collapse into one — host uses its host key for both — but the spec should
  allow them to be separate for fleets where one account key manages many
  host keys.
- **Rate limiting / abuse.** CSR signature prevents bystanders from
  initiating enrollment for arbitrary hosts (they'd need the private key).
  Still worth defining lightweight rate limits so the CA isn't weaponized
  into a connection generator.
- **Multiple names per host.** One authorization per name, SSH callback per
  name. Operationally fine, worth defining cleanly.
- **Non-standard SSH ports.** CSR should include the port.
- **Network reachability.** CA must be able to reach the host on SSH.
  Limits NADIR-SSH-01 to publicly-reachable hosts, same as ACME HTTP-01.
  Other challenge types would cover behind-NAT cases.
- **Short-lived certs as the norm.** Design renewal to be cheap and
  frequent. Align with the cultural shift ACME drove for TLS.
- **KRL (Key Revocation List) distribution.** SSH's CRL equivalent. Worth
  considering whether NADIR specifies a standard endpoint for KRL fetch.
  Probably v2 material but the spec has room for full lifecycle.

- HashiCorp Vault SSH secrets engine
- Teleport machine ID
- Netflix BLESS
- Facebook's SSH CA setup (blog posts)
- Uber's pam-ussh
- SPIFFE/SPIRE workload identity (for the attestation model)
- Any IETF curdle or secsh WG drafts on SSH cert enrollment

## Client-side trust distribution (out of NADIR scope)

SSH has no cert store analogous to OS-level TLS trust stores, and NADIR is
not going to invent one. Client trust in CA keys is left to operators and
tooling.

### Epithet's role

When the client is an epithet user, epithet can handle this naturally:

- Epithet agent already receives a list of hostname patterns during
  discovery.
- Those patterns map cleanly onto `@cert-authority` line scopes in
  known_hosts.
- The CA's public key is always available at the configured epithet CA URL
  (fetched over TLS, with the TLS cert chain establishing authenticity).
- Epithet agent can maintain `@cert-authority` entries in the user's
  known_hosts — one per authoritative hostname pattern — pointing at the
  current CA pubkey.
- Rotation handles itself: next discovery cycle, agent fetches current CA
  pubkey, updates entries. No operator intervention on CA key rotation.

### For non-epithet clients

Falls back to "operator puts the CA key in known_hosts somehow" — Ansible,
Chef, Puppet, manual distribution, whatever fits the shop. This is the
status quo for SSH CA deployments and works fine.

## Summary of the ecosystem shape

```
epithet (project)
├── CA
├── SSH agent
├── built-in simple policy server (principal == username)
├── client-side trust management for @cert-authority entries
└── NADIR client (for getting host certs)

writ (separate project)
├── policy server (principal == {host, user})
├── host agent (local account discovery, reporting)
├── SCIM integration
├── bastion (session mediation, termination)
└── implements NADIR server for hosts it's authoritative over

NADIR (independent protocol spec)
├── spec document (the primary deliverable)
├── reference implementation (TBD — maybe lives with writ initially)
└── adoption path: writ implements it; eventually others might too
```
