# Writ architecture — session 4

Builds on `1.md`, `2.md`, and `3.md`. Working notes, not commitments.

## Cedar: mechanism solved, decision unchanged

Session 3 set Cedar aside for two reasons. Investigating both:

1. **"Obligations need partial evaluation, which is experimental."**
   **Void.** Partial evaluation is not needed — cedar-go's stable public
   API already has a sufficient hook for async fact resolution. The
   mechanism is documented below because it is a real finding worth
   keeping, and because it preserves Cedar-as-a-backend as a future
   option.
2. **"Cedar is verbose for SSH access, so we need a DSL anyway, and
   DSL + Cedar is worse than DSL + simple evaluator."** **Confirmed, and
   decisive.** See the adoption and cost/benefit sections below.

**Net: session 3's conclusion stands.** Build the pf-inspired DSL with
writ's own evaluator. But three things from this session's Cedar work
carry forward regardless of engine, and one of them turns out to be a
real argument *for* the DSL rather than a concession to it.

## Does Cedar have UDFs? No — and it never will

Worth writing down so it doesn't get re-litigated.

Cedar has no user-defined functions: no `function`, no lambdas, no
recursion, no set comprehension (no `map`/`filter`/`fold`/`any`/`all` —
only `contains`, `containsAll`, `containsAny`). This has been requested
repeatedly and deferred repeatedly.

The reason is Cedar's whole value proposition: **decidability**. Cedar
policies compile to SMT via the symbolic compiler, so you can ask a
solver "is policy A strictly more permissive than B?" or "can this
policy ever permit X?". A UDF is opaque to a solver. Cedar also
guarantees termination and purity, which UDFs break. This is a
deliberate exclusion, not an unimplemented feature.

What exists instead:

| Mechanism | Usable as a UDF? |
|-----------|------------------|
| Extension functions (`ip`, `decimal`, `datetime`/`duration`) | No — closed set, no registration API. Adding one means forking |
| Entity attributes / tags | Yes, effectively — this is the intended extension point |
| Entity hierarchy + `in` | Grouping only |
| Templates | Parameterization, not computation |
| Annotations (`@key("value")`) | Not computation, but useful for obligations |

Critically: even a forked extension function **could not be async**. The
evaluator calls it synchronously with no `context.Context` and no
suspension point. Facts have to be resolved outside evaluation
regardless. That constraint is what shapes everything below.

## The mechanism: async facts via a lazy EntityGetter

### The idea

An unresolved fact evaluates to `false`, and the act of asking for it
triggers the async work that will eventually resolve it. Fire an
evaluation, capture which async facts are in play, and as each result
arrives, re-fire and ask "did that change the answer?"

### Why it works on the stable API

Verified against **cedar-go v1.8.0**:

```go
// types
type EntityGetter interface {
	Get(uid EntityUID) (Entity, bool)
}

// authorize.go
func Authorize(policies PolicyIterator, entities types.EntityGetter,
                req Request) (Decision, Diagnostic)
```

`EntityGetter` is an *interface*; `EntityMap` is merely the trivial
implementation. The stable top-level entry point accepts the interface.
So writ supplies its own resolver — **no fork, no `x/exp`**.

And `Get` is called **lazily, inside `Eval`, at the moment the AST node
is reached**. Confirmed at four call sites in `internal/eval/evalers.go`:
`attributeAccessEval.Eval()`, `getTagEval.Eval()`, `hasTagEval.Eval()`,
and the `in` parent-traversal helpers `entityInOne()`/`entityInSet()`.

Because Cedar specifies `&&` as short-circuiting left-to-right, a fact
sitting behind a failed guard is **never fetched and never triggers its
side effect**. That is pull-style laziness inside a declarative policy —
the thing an eager prefetch design cannot give you.

### Sketch

```go
func (r *factResolver) Get(uid types.EntityUID) (types.Entity, bool) {
	if uid.Type != "Fact" {
		return r.static.Get(uid)   // hosts, groups, principals
	}
	f := r.facts.lookup(uid)       // unstarted | pending | settled
	if f.state == unstarted {
		r.trigger(uid)             // async work, deduped by uid
	}
	if f.state != settled {
		r.inPlay.add(uid)
		return factEntity(uid, false), true
	}
	return factEntity(uid, f.value), true
}
```

The resolver is constructed **per request**, so it closes over the
request. `Fact::"oncall"` in a policy therefore means "is *this*
principal oncall." The policy names the fact; the resolver binds it to
the request. Clean separation, and it keeps request identity out of the
policy text.

### The refire loop

```
for {
    inPlay.reset()                        // recompute each pass
    decision, diag := cedar.Authorize(policies, resolver, req)

    if len(diag.Errors) > 0       -> 500  // fail closed
    if decision == Allow          -> 200
    if inPlay.allSettled()        -> 403  // real deny, nothing pending
    if inPlay.anyHumanTimescale() -> 202  // emit event, broker retries

    wait for next arrival                 // "did that change the answer?"
}
```

## Three properties that make it sound

### 1. Monotonicity — `false` is not `unknown`

Defaulting an unresolved fact to `false` is safe **only if resolving it
`false → true` can only widen access**. Cedar is forbid-overrides-permit,
so negation position matters:

```cedar
permit (...) when { Fact::"oncall".value };
// unresolved -> no permit -> deny. Safe.

forbid (...) when { !Fact::"approved".value };
// unresolved -> forbid fires -> deny. Safe.

forbid (...) when { Fact::"high_risk".value };
// unresolved -> forbid SKIPPED -> permit. FAIL OPEN.

permit (...) unless { Fact::"high_risk".value };
// same hole via negated unless. FAIL OPEN.
```

Stated generally: the decision must be **monotone non-decreasing in
permissiveness** as facts go `false → true`. Syntactically, each fact
reference must sit under an even number of negations in a `permit` and an
odd number in a `forbid`.

This is checkable statically. The `ast` package is construction-only (no
walker, no introspection), but `Policy.MarshalJSON()` emits Cedar's
specified JSON policy format, which is a fully structured AST. So the
lint walks that — a spec-level dependency rather than library internals.
Reject non-monotone policies at load time.

Monotonicity does triple duty:

- makes `false`-as-unknown sound
- guarantees the refire loop converges without oscillation
- makes a `Permit` from *any* pass final and immediately actionable,
  without waiting for still-pending facts to settle

### 2. Never return `(_, false)` for a fact

The resolver must always return a real `Entity` with `value: false`,
never "not found." Confirmed semantics:

| `Get` returns | Attribute access | `hasTag` | `in` traversal |
|---|---|---|---|
| `(entity, true)` | reads attribute | checks tag | walks parents |
| `(zero, false)` | `errEntityNotExist` → **policy skipped** | `types.False`, no error | continues, no path |

And in `authorize.go`, a policy that errors is appended to
`diag.Errors` and `continue`d — **including forbid policies**. So a
not-found fact silently deletes a `forbid` rule. That is fail-open.

Two consequences:

- the resolver never returns `(_, false)` for a `Fact::` UID
- writ treats a non-empty `diag.Errors` as fail-closed, not as noise

Also: the lint should reject facts reached via `hasTag`, whose fail-soft
`types.False`-on-missing behaviour defeats the invariant.

### 3. Three states internally, two states in Cedar

A resolver that definitively answers "no" is indistinguishable from one
that hasn't answered yet, once flattened to a Cedar boolean. So facts
need `unstarted | pending | settled{value}` internally even though Cedar
only ever sees `true`/`false`. That third state is exactly what
distinguishes **403 from 202**.

## Why laziness is load-bearing, not an optimization

`inPlay` is recomputed on every pass, and the set *grows* as facts
resolve. Pass 1 touches `oncall` and short-circuits. Once `oncall` flips
true, pass 2 proceeds further and touches `approved` for the first time.

So **an approval request is only ever created after every cheaper
condition has already passed.** An eager-prefetch design would page a
human for rules that turned out not to apply. That is user-visible spam,
and it is the reason the lazy resolver is worth the impurity.

Splitting facts by whether their resolver has side effects:

- **Read-only** (`oncall`, `mfa_recent`) — over-fetching costs one wasted
  API call. Harmless.
- **Side-effecting** (`approval` — creates a request, pages a human) —
  over-fetching is spam. Genuinely needs laziness.

Latency class (`fast` | `human`) and side-effect-ness are properties of
the **handler**, declared in writ's fact registry. Not policy-language
concerns.

## The loop is fractal — and 2.md already specified the outer half

Two timescales, one mechanism:

- **Fast facts** (oncall, ~100ms) — converge in the inner in-process
  loop, before the HTTP response is written.
- **Human facts** (approval) — exit to `202` + `retryAfter`. The
  broker's full retry becomes the next iteration of the same loop.

Because `2.md` already specified stateless re-evaluation on retry, the
outer loop needs **no new protocol surface**. The 202 design and the
refire design are the same design at different frequencies.

## Costs of a side-effecting evaluator

Honest accounting — this is the price of the approach:

- **Not idempotent.** Refiring re-invokes handlers, so a request-scoped
  fact cache keyed on the fact UID is mandatory, or each pass pages the
  human again.
- **Not cacheable.** `Authorize` results can't be memoized across
  requests.
- **Testing has side effects.** Policy dry-run needs an explicit
  no-side-effects mode, or the test suite pages oncall.
- **Analyzability lost for fact-bearing rules.** The SMT analyzer can't
  see through an opaque fact. Rules without facts remain analyzable.

Note: epithet already has a precedent for in-flight dedup —
`5a4123f fix: share in-flight auth attempt across ssh sessions and kill
abandoned flows`. Same shape of problem.

## Also confirmed

- `Diagnostic.Reasons` contains **all** satisfied policies of the winning
  class (all matched forbids if any forbid matched, else all matched
  permits) — not a single determining policy. So the annotation approach
  below can collect `@require` from every permit that fired.
- **Annotations as obligations** remains available as an alternative or
  complement: `@require("approval")` on the policy, read back from
  `Reasons` → `Policy.Annotations()`. Obligation becomes syntactic (the
  property `3.md` liked about pf) with no partial eval. Moot given the
  decision below, but recorded because it is the better of the two
  approaches if Cedar is ever revisited as a compilation target.
- `x/exp/eval` **does** still exist in `main` (alongside `batch`, `ast`,
  `dot`, `schema`, `types`); pkg.go.dev's "not in the latest version"
  note was a tagging artifact. But `x/exp/README.md` still disclaims
  semver, so session 3's judgment was correct — it simply no longer
  matters.
- cedar-go v1.8.0 nudges writ toward Go again, as `2.md` anticipated.

## Cedar adoption: thinner than the messaging

Checked because "adopt the standard" is only an argument if the standard
is actually standard. Primary sources, not vendor marketing:

- **CNCF Sandbox**, accepted 8 October 2025 — the *lowest* maturity tier.
  OPA, for comparison, is Graduated.
- The project has **no `ADOPTERS` file**. Cedar's own CNCF Sandbox
  application (`cncf/sandbox#371`) says so explicitly.
- That application names exactly four external companies — Cloudflare,
  MongoDB, StrongDM, Cloudinary — with no scope, scale, or case studies,
  and does **not** distinguish production deployment from evaluation. It
  asserts "widespread deployment" with no metrics behind it.
- The CNCF project page lists **no adopters at all** — purely a technical
  description.
- One real third-party integration found: the Janssen authorization
  server.
- The ~1.17M downloads figure in circulation traces to StrongDM's own
  Cedar guide — an adopter with a commercial interest in the category.
  Crate/module download counts conflate CI regardless.

Outside AWS's own services (Verified Permissions, Verified Access) and
AWS Labs' Kubernetes webhook, that amounts to four unelaborated logos and
one integration. A credible early-stage project with a strong corporate
sponsor — not a language writ's operators will have encountered.

Indirect corroboration of the verbosity complaint: there are 2026 papers
on *automatically synthesizing* Cedar policies (AutoCedar;
autoformalization of instructions into policy-as-code). Synthesis papers
don't get written for languages that are pleasant to hand-author.

## Why adoption settles it

The four reasons to adopt a general standard over a domain language,
scored for writ:

| Reason | Writ |
|--------|------|
| Operators already know it | **No.** The audience knows `pf.conf`, `sudoers`, `iptables`. Nobody arrives knowing Cedar |
| Ecosystem tooling | Real, but AVP-centric (console, playground). Little of it serves a self-hosted SSH policy server |
| Portable artifacts / interop | **No.** Nobody moves Cedar policies between writ and anything else |
| Formal analyzability | The genuine payoff — AWS shipped Cedar Analysis as OSS tooling |

The fourth row is where the argument collapses, and the reason is
specific to writ's design rather than a general objection to Cedar:

**A `Fact::` lookup backed by an async resolver is opaque to the SMT
analyzer** — the same reason Cedar refuses UDFs at all. So analyzability
is forfeited precisely on the fact-gated rules, which are the rules writ
exists to express and the ones most worth machine-verifying.

Cedar's one non-negotiable advantage is neutralized on writ's
distinctive feature. What remains is a fast evaluator plus a verbose
general-purpose language plus a dependency, for a domain — identity ×
host × account, with obligations — narrow enough that generality is dead
weight.

The comparison also has to be honest about what writ would actually be
building instead. Not an interpreter — a matcher over a three-element
tuple with globs, plus obligation checks. `epithet/pkg/policy/policy.go`
already does a first cut in 46 lines using `doublestar`. The choice is
not "Cedar vs. writing Rego."

## Decision: pf-inspired DSL, writ's own evaluator

Session 3's conclusion stands. Cedar is not adopted — neither as
authoring surface nor as engine.

Keep the evaluator behind an interface so the DSL is the authoring
surface while the backend stays swappable. If writ's domain later grows
toward arbitrary attribute expressions, Cedar-as-a-compilation-target
remains available and the mechanism sections above document exactly how.

### What carries forward regardless of engine

**1. Monotonicity — and it is an argument *for* the DSL.**

The requirement arose from Cedar's `false`-as-unknown, but it applies to
any evaluator with async facts: resolving a fact must only ever widen
access, or the loop can oscillate and an unresolved fact can fail open.

In Cedar this needed a static lint over the JSON AST, because a fact
reference can appear anywhere in an arbitrary boolean expression at any
negation depth. In a DSL where obligations are explicit syntax, **the
fail-open forms are not expressible at all** — a `require` can only
withhold permission, never grant it. Monotonicity holds structurally, by
construction, with no lint and nothing to enforce.

This is the strongest technical argument for the DSL, and it only became
visible by working through the Cedar version. `3.md` argued
obligations-as-syntax on ergonomic grounds; the soundness argument is the
better one.

**2. Three-state facts.** `unstarted | pending | settled{value}`. A
handler that definitively answers "no" must be distinguishable from one
that has not answered yet. This is what separates 403 from 202, and it is
engine-independent.

**3. The refire loop and the fast/human split.** Latency class
(`fast` | `human`) and side-effect-ness are properties of the *handler*,
declared in writ's fact registry — never policy-language concerns.

```
for {
    touched.reset()
    result := evaluate(rules, state, resolver, req)

    if result == allow             -> 200
    if touched.allSettled()        -> 403   // real deny, nothing pending
    if touched.anyHumanTimescale() -> 202   // emit event, broker retries

    wait for next arrival                   // "did that change the answer?"
}
```

Two properties of this loop are worth stating explicitly because they are
easy to lose in a rewrite:

- **Recompute `touched` every pass.** The set *grows* as facts resolve:
  pass 1 checks `oncall` and stops; once `oncall` settles true, pass 2
  reaches `approval` for the first time. So an approval request is only
  ever created after every cheaper condition has already passed. Eager
  resolution would page a human for rules that never applied.
- **Dedup by fact identity.** Refiring re-invokes handlers, so a
  request-scoped cache is mandatory or each pass pages the human again.
  Precedent in epithet: `5a4123f fix: share in-flight auth attempt
  across ssh sessions and kill abandoned flows`.

A DSL evaluator gets the laziness Cedar got from `&&` short-circuiting
for free: evaluate `require` clauses after the match clauses, and stop at
the first unsatisfied one.

**4. Fail closed on evaluator errors.** Cedar's `Authorize` silently
skips erroring policies *including* `forbid` rules, which is fail-open.
Writ's evaluator must treat any rule-evaluation error as a hard failure,
never as a non-match. Worth writing a test for early — it is the kind of
thing that regresses invisibly.
