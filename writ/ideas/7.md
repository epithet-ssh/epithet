# Writ policy language — session 7: the IL contract

Builds on `6.md`, which specified the C′ frontend and deliberately left
the IL to this session. Scope here is narrow on purpose: the four
decisions that block a spike, plus the consequences they force back onto
session 6's frontend spec. The evaluator, dry-run, and handler questions
are session 8.

## What this session settled

| # | Question | Decision |
|---|---|---|
| — | Negation placement in the IL (6.md carry 1, Q10) | **Two types** — negation is unrepresentable on the allow path, not merely rejected |
| — | Glob vs exact matcher values | **Globs match names, never attribute values**; a quoted value is always a literal |
| — | Case sensitivity | **Byte-exact everywhere**; host names ASCII-lowercased at three boundaries |
| — | Content-id derivation (6.md carry 1) | **SHA-256 over a canonical projection** of the IL; `label` excluded |
| — | Duplicate rules | **Warn and collapse**, naming both source lines — labels are cosmetic |
| — | Grant labels (6.md carry 3) | **No synthetic labels** — the content id is the handle, display strings derive at render time |

## Decisions and rationale

### Negation is a type distinction, not a validated field

Session 6 argued at length that deny-only negation had to be a
grammar-level restriction — separate `allow-head` and `deny-head`
productions — rather than a post-parse check. That argument does not stop
at the parser. 5.md's framing is that **the IL is writ's real policy
interface and the surface syntax is one frontend over it**; a restriction
enforced only in the frontend is a restriction on one of N producers.

So the IL splits the type:

```go
type MatchSet struct { Or []Matcher }

type NegatableMatchSet struct {
	Not bool
	MatchSet // A negatable set is a set plus a bit.
}
```

Allow rules carry `MatchSet` in all three positions. Deny rules carry
`NegatableMatchSet`. A negated allow has no field to set — it is
unrepresentable rather than rejected, and no validator has to stay
correct forever for the property to hold.

The alternative considered was one uniform type plus a validator
rejecting `Not: true` on allows. It is equivalent for the compiler this
session is specifying and diverges for every other IL producer: the
grants CLI, a future web UI, a hand-edited event replay. Grants are the
concrete case — they are IL-native and allow-only, so they take
`MatchSet` and become structurally incapable of expressing negation
without a single check being written.

5.md's IL sketch put "an optional negation flag" on each individual
matcher. That is now rejected outright: a per-matcher flag inside a
disjunction can express exactly `[!$sre, !$dba]`, the De Morgan footgun
6.md made a syntax error. Negation belongs to the whole expression,
matching `!`'s position in the grammar.

Cost accepted: deny rules and allow rules are not the same shape, so IL
walkers branch. They were already not the same shape — `until`, `ttl`,
and `require` are allow-only per 6.md — so the marginal cost is near zero.
The embedding keeps the shared part addressable: code that does not care
about negation takes the inner `MatchSet` and needs no branch at all.

### Globs match names, never attribute values

Two of the four glob positions were already settled and stay settled:
account names glob (5.md: inventory-grounded matching is "uniform for
literal and glob matches") and host names glob (6.md reasons explicitly
about `*` in host names).

The open positions were SCIM tag values (`group:SRE*`, `id:"*@corp.com"`)
and label-selector values (`{env=prod*}`). Both lex and parse today
because bare words admit `*` and `?`. Both are now **exact**.

The criterion is the one that decided negation: **monotonicity under
drift.** A matcher whose set grows as an external system grows is
fail-safe on a deny and fail-open on an allow. `group:SRE*` is precisely
that mechanism on the allow path — someone creates `SRE-Interns` in the
IdP and a rule granting root silently covers them, with no policy change
and no reviewer seeing anything. A trailing `*` is markedly *less* visible
in review than a leading `!`, which 6.md banned for the same reason.

Two supporting arguments:

- **Globbing `id:` contradicts opaque identity.** 5.md is emphatic that
  writ never interprets the identity value — it is compared byte-for-byte
  against one configured SCIM attribute, which a deployment may point at
  `sub`. `id:"*@contractors.example.com"` is email-domain semantics
  smuggled in through pattern matching, and its meaning silently
  evaporates when the identity claim is reconfigured.
- **The grouping mechanism already exists.** Every real use for
  `group:infra-*` is served by `user infra = [group:infra-core,
  group:infra-net]` — more text, but visible in review and lintable
  against the inventory, since 6.md already warns on a `group:` matching
  no synced group.

Label-selector values are the weaker case, because hosts are writ's own
inventory rather than an external system, so the drift argument does not
bite as hard. They are excluded on a different ground: `{env=prod*}` is a
workaround for a label taxonomy that should have been `{env=prod}` plus a
second key, and multi-key AND selectors already solve it properly. Host
*names* keep their globs because names are organically assigned and
cannot be fixed by discipline.

**A quoted attribute value is always a literal.** `group:"weird*name"`
matches a group with a star in its name. A bare `*` or `?` in an
attribute-value position is a well-formedness error, so the common
mistake gets a pointed diagnostic while the rare real case stays
expressible.

### Byte-exact comparison, with host names normalized at the boundary

One comparison rule in the evaluator: **byte-exact.** No matcher carries a
case-sensitivity mode.

Host names are the exception, and they are handled by normalizing rather
than by folding at compare time. Host names are ASCII-lowercased at three
ingress points — registration (`PUT /api/v1/hosts/{name}`), request
resolution (`remoteHost` off the connection block), and policy
compilation — so everything downstream is already normalized and the
matcher stays a byte compare.

The reason hosts get this and nothing else does: **a host name is a lookup
key into writ's own namespace, arriving from three directions that
disagree about case** — the agent's self-reported hostname, whatever the
user typed at the ssh prompt, and the policy file. An account name is the
opposite: it is a value writ signs into the certificate principal, checked
byte-for-byte by sshd against the host's account inventory. Case-folding a
lookup key is hygiene; case-folding a signed value would have writ issue
certs for principals that do not exist.

**The fold is ASCII-only** — `A-Z` to `a-z`, every other byte untouched.
Not Unicode case folding, which is locale-dependent (Turkish dotless *i*)
and Unicode-version-dependent, so a stdlib upgrade could silently change
which hosts a rule matches. This is 6.md's timestamp principle — "a policy
file must not mean different things on different machines" — applied to
the second place it bites.

**SCIM attribute values and label keys and values stay byte-exact**, on
the theory that the inventory-aware linter is a better safety net than
folding. 6.md already warns when a `group:` matches no synced group and
when a `{}` selector matches no registered host. That catches `group:sre`
against an IdP's `SRE` *and* catches `group:SER`, which folding never
would. The split is strict semantics with generous diagnostics: match
exactly, and have the error say "no group `sre` — did you mean `SRE`?"

Keywords are lowercase-only, and this needs no rule: `DENY` lexes as a
bare word, and a bare word at statement start is already a parse error
under 6.md's LL(1) property.

Considered and cut: a confusables lint for `$prod` versus `$PROD`, which
6.md's redefinition-is-an-error check would not catch. Not worth a rule.

### Content ids hash a canonical projection

6.md established that every compiled IL rule carries a content-derived
stable id, with `label` as a purely human-readable alias over it. This
session fixes the derivation.

**Over the IL, not the source text** — 6.md's own reasoning, confirmed:
hashing source would churn ids on a reformat or a macro rename, which is
exactly what a stable id exists to prevent.

**Canonicalize for hashing only, never in the stored IL.** The id is
computed over a canonical *projection* of the rule: disjunction lists
sorted, `require` / `when` / `notify` lists sorted, label-selector maps
key-sorted. Heterogeneous matchers sort bytewise by their own canonical
encoding, which is total and needs no kind-ordering table. The stored IL
preserves source order.

That split is load-bearing. Sorting the IL itself would force `fmt` to
sort the source to match — and reordering `require [oncall, approval]`
fights an author who deliberately put the cheap check first, while
reordering `[ubuntu, deploy]` destroys meaningful emphasis. Canonicalizing
only the hash input makes `[$sre, $dba]` and `[$dba, $sre]` correctly one
rule with one id, leaves every authored list alone, and keeps 6.md's "fmt
never changes the compiled IL" true without adding a sort rule to the
formatter.

**`label` is excluded from the hash. Everything else is in** — `effect`,
all three matcher positions, `require`, `when`, `until`, `ttl`, `notify`.
Hashing the label would be circular, since 6.md defines it as an alias
*over* the id: rename a label and every prior audit event points at a rule
that no longer exists. `notify` stays in despite not affecting the access
decision, because it changes what the system does.

**Canonical JSON: sorted keys, no insignificant whitespace, empty and null
fields omitted, `ttl` as integer seconds, timestamps as RFC 3339 UTC with
`Z`. The schema version is deliberately not hashed.** 5.md requires the IL
to carry a schema version from day one; if that were in the hash, every
schema bump would churn every id in every deployment and break audit
continuity across upgrades — the one thing content ids exist for.
Omit-empty extends the same property to additive evolution: a v2 that adds
an optional clause changes ids only for the rules that actually use it.

**Full SHA-256 stored; displayed as 12 lowercase hex characters; the CLI
accepts any unambiguous prefix.** The git model, for an audience that
already has the reflex.

### Duplicate rules warn and collapse

With `label` excluded from the hash, two rules differing only by label
produce the same id, as do two literally identical rules. The IL is a set
keyed by id, so a duplicate collapses on its own. **Apply warns, naming
both source lines, and proceeds.** The surviving rule keeps the first
label in source order — a display choice, and source order is the only
non-arbitrary tiebreak.

An earlier draft made this an error, on the grounds that only one label
could appear in a future 202 or page and picking one silently was an
arbitrary semantic choice. That argument does not survive the actual
position on labels: a label is a convenience alias, never an identifier,
and a rule with no usable label is logged as itself. A label collision is
therefore cosmetic, and the collapse loses nothing that was not already
recoverable from the rule.

What remains worth saying is the lint. Two rules that compile to one are
usually a copy-paste the author did not finish editing, so the warning
names both lines and says they are identical — the useful information —
without blocking an apply over a provable no-op.

### Grants need no synthetic labels

6.md carry 3 asked whether grants get synthetic labels
(`grant:carol:prod-db-1`) for 202 messages, or whether the content id
serves. It closes as a consequence of the above: grants are IL-native
allow rules and hash identically, and because a grant's IL carries its
absolute `until`, repeat grants of the same access get distinct ids
naturally.

No synthetic labels. A 202 message should name the *requirement* — "waiting
on approval from your manager" — not the rule, and a grant's
human-readable handle derives at render time from its own fields rather
than being stored.

## The IL

JSON shapes below; the Go structs are the real definition, per 5.md.

### Rule shapes

An allow rule:

```json
{
  "schema":   1,
  "id":       "a3f9c1d2e8b4",
  "effect":   "allow",
  "label":    "sre-prod-root",
  "users":    {"or": [{"group": "SRE"}]},
  "accounts": {"or": [{"name": "root"}]},
  "hosts":    {"or": [{"labels": {"env": "prod"}}]},
  "require":  ["oncall", "approval"]
}
```

A deny rule — note `not` on the expression, never on a matcher:

```json
{
  "schema":   1,
  "id":       "7c1e0b93a5df",
  "effect":   "deny",
  "label":    "prod-freeze",
  "users":    {"not": true, "or": [{"group": "Infrastructure"}]},
  "accounts": {"or": [{"any": true}]},
  "hosts":    {"or": [{"labels": {"env": "prod"}}]},
  "when":     ["freeze"]
}
```

`or` is the disjunction (the surface language's union lists); `not` exists
only on deny rules and applies to the whole disjunction.

### Matcher taxonomy

| Position | Kinds |
|---|---|
| `users` | `{"id": s}` `{"group": s}` `{"type": s}` `{"dept": s}` `{"org": s}` `{"any": true}` |
| `accounts` | `{"name": s}` `{"glob": s}` `{"any": true}` |
| `hosts` | `{"name": s}` `{"glob": s}` `{"labels": {k: v}}` `{"any": true}` |

All string values are compared byte-exact. `glob` supports `*` and `?`
only, per 6.md. Host `name` and `glob` values are stored ASCII-lowercased.

`*` compiles to `{"any": true}` rather than `{"glob": "*"}` in every
position. It is semantically distinct, it lets the evaluator skip the glob
engine for the common wildcard, and it gives the linter a token to
recognize — 6.md carry 2 flags `*` in user position as the one remaining
matcher that grants to everyone including future users, and that lint
needs something to match on.

### Canonical form

The hash input for the allow rule above, with `schema`, `id`, and `label`
dropped, empties omitted, object keys sorted, and **every list sorted and
deduplicated** — match sets, `require`, `when`, and `notify` alike:

```
{"accounts":{"or":[{"name":"root"}]},"effect":"allow","hosts":{"or":[{"labels":{"env":"prod"}}]},"require":["approval","oncall"],"users":{"or":[{"group":"SRE"}]}}
```

`id = hex(sha256(canonical))[:12]` for display; the full digest is stored.

Sorting every list, rather than `require` alone, is forced by lists being
sets: `[$sre, $dba]` and `[$dba, $sre]` are the same rule, and an id that
disagreed would make reordering a line look like authoring a new rule.
Union and conjunction are both commutative and idempotent, so the sort is
semantics-preserving in every position.

Source order is still never touched — canonicalization happens in the hash
input only. The consequence is that two IL values equal as sets can differ
as structs, so **IL comparison must be canonical, not structural.** Nothing
should compare rules with a deep-equality helper.

## Amendments to session 6

These follow from the decisions above and supersede the corresponding
text in `6.md`.

**Grammar.** Five corrections, all gaps rather than changes of intent:

- **Statements are terminated in the grammar, not just the lexer.** 6.md's
  EBNF has no terminator in any production, so two adjacent rules have no
  boundary. `rule = ( allow-rule | deny-rule ) TERM` and `macro-def = ...
  TERM`, where `TERM` is the token the rule below defines.
- **`timestamp` and `duration` are not terminals.** 6.md lists them as
  lexical tokens, but its own text makes durations bare words disambiguated
  by following `ttl`, and timestamps quoted strings parsed as RFC 3339. Both
  are ordinary tokens (`bare`, `string`) with a parse-time validation, and
  listing them as terminals invites a context-sensitive lexer that is not
  needed.
- **`$` is its own token.** The lexer emits `$` followed by `bare`; the
  parser checks the `bare` is `ident`-shaped. Lexing `$ident` as one token
  would silently stop at the `.` in `$foo.bar` instead of diagnosing it.
- **Trailing commas are legal inside `[]` and `{}`.** `[a, b,]` parses. At
  bracket depth zero a trailing comma still drives continuation, so one
  before EOF promises a clause that never arrives and is an error.
- **Lists are sets, and expansion flattens.** A macro whose body is a list
  may appear in atom position: with `user sre = [group:SRE, group:Infra]`,
  `[$sre, group:X]` is a three-element set, not a nested one. Order carries
  no meaning and duplicates collapse, so the AST node in a match position is
  an expression, never a fixed-arity atom.

**Statement termination.** 6.md stated implicit continuation in prose; the
lexer rule is: *comments are stripped first, then a newline emits a
statement terminator when bracket depth is zero and the previous
significant token is not a comma. EOF is a statement terminator.* Stripping
comments before the test is what makes a trailing comment after a trailing
comma behave — `require [a, b],  # why` still continues the rule.

**Labels.** 6.md's stated reason for keeping labels lint-only — "an urgent
apply should not block on a naming requirement" — was never the actual
reason, and is superseded here. Labels are optional because a label is a
convenience alias and a rule with no label is logged as itself; there is no
audit gap for one to close, so the requirement 6.md rejected as
inconvenient should have been rejected as pointless. This session makes that mechanically free:
since `fmt` renders as a pure function of the IL, every rule has a
canonical human-readable rendering derivable on demand — no source spans
stored, no source text retained.

**Formatter.** Three changes:

- Quoting is a **rendering decision, not stored state** — the IL holds
  strings, and nothing records whether the author wrote quotes. The
  formatter emits them iff the bare rendering would not lex back to the
  same value *in that position*, and strips them otherwise. Being a total
  function of value and position, identical IL always formats identically,
  which is what 6.md wanted when it said quoting in formatted output should
  signal "this value contains something interesting" — a preserved but
  unnecessary quote signals nothing. The predicate subsumes 6.md's special
  cases: `@` in `id:"carol@example.com"`, `:` in timestamps (which "must"
  keep quotes as a consequence rather than an exception), a trailing `-`,
  the empty string. What changed is that "bare-word-legal" became
  position-dependent once globs were restricted to names — `weird*name` is
  inside the bare-word charset but illegal in an attribute-value position —
  so `group:"weird*name"` is quoted whether or not the author wrote it that
  way, while account and host globs are not.

  `fmt` on input that parses but fails well-formedness must **not**
  synthesize the quotes that would make error 10 go away. It renders the
  token as authored and the error is reported separately; a formatter that
  silently repairs an ill-formed security policy is worse than one that
  leaves it ugly.
- Host names and host-position globs are ASCII-lowercased. Account names,
  label keys, label values, and tag values are left alone.
- Lists are never reordered, and never emitted with a trailing comma even
  though one parses. Canonicalization happens in the hash input, not the
  source.

**Well-formedness errors**, appended to 6.md's list:

10. A bare `*` or `?` in an attribute-value position — a `user-tag` value,
    a label key, or a label value. Globs remain legal in account names,
    host names, and as a standalone `*` atom. This is a well-formedness
    check, not a lexical one: the lexer cannot see position.
11. A trailing comma at bracket depth zero immediately before EOF.

**Warnings.** 6.md's warning 1 — a rule carrying `require` / `when` /
`notify` with no `label` — is **removed**, and 6.md's remaining warnings
renumber. It was the only warning in that set reporting a style opinion
rather than a fact about the world (a dead notify target, an unreferenced
macro, a selector matching no host), and with labels established as
cosmetic it fired on correct policy — which is how a lint teaches people
to ignore warnings. Added in its place: two rules with identical content
ids, naming both source lines, and a duplicate atom within one authored
list. The second fires only on duplicates the author wrote — duplicates
arising from macro expansion are ordinary composition and collapse
silently.

## Carried forward to session 8 (the evaluator)

Unchanged from 6.md's list: **Q5** dry-run, **Q8** whether to commit to a
Datalog-shaped IL, **Q9** handler packaging and a contrib set, plus 6.md
carry 2 (`*` in user position) and carry 4 (requirement/flag/notify name
resolution when a handler is deregistered while policy still names it).

**Q6** (duplicate SCIM group displayNames) is treated as answered by
5.md's own text — union with a loud sync-time warning — unless session 8
wants to revisit it.

**Q10 remainder**: schema versioning and migration story. The
"authoritative or re-derivable" half is now easier: with canonicalization
fixed and macros expanded at compile time, compilation is deterministic,
so the IL stored in `PolicyUpdated` is reproducible from the stored source
and storing it is an optimization rather than a necessity.

New, raised by this session:

1. **Prefix-ambiguity scope for ids.** Is a 12-hex prefix required to be
   unambiguous within the current policy version, or across all history in
   the event log? The former is cheap and the latter is what an auditor
   reading an old event actually needs.
2. **Grant amendment and id churn.** A grant's `until` is in the hash, so
   extending a grant produces a new id. That is correct by 6.md's rule
   ("an edited rule getting a new id is correct — it is a different
   rule"), but the revocation and audit story should say how the two are
   linked.
3. **Authored or expanded form in logs.** A rule renders from its IL,
   which is post-macro-expansion, so a log line shows the expanded
   disjunction rather than `$sre`. That is arguably the better audit
   artifact — it says what actually matched — but it is not what the
   author wrote, and a 403 investigation may want both.
4. **Where normalization is enforced.** Host-name lowercasing at three
   boundaries is easy to implement twice and forget the third time. Worth
   a single chokepoint type rather than three call sites.
