# Writ architecture — session 2

Captured from a design conversation. Builds on `1.md`. Working notes, not
commitments.

## Settled decisions

### State model: event sourcing / prevalence

All state changes are events in an append-only log. Current state is an
in-memory projection rebuilt by replaying the log on startup. Snapshots are
an optimization for later.

Rationale: SSH access is a domain where a complete audit trail isn't a
nice-to-have — it's the point. Event sourcing makes the audit log the
source of truth rather than a secondary concern bolted on. The expected
state sizes (thousands of hosts, hundreds of users, tens of thousands of
mappings) fit comfortably in memory.

The journal format (JSON lines, binary, etc.) is deliberately deferred.
The event types and projections come first — serialization is mechanical
once you know the shape.

Storage backend is an open question. Postgres was discussed but isn't
settled — SQLite, embedded KV, or the prevalence model's own journal
file are all viable. The event-sourced design means the storage layer is
thin (append events, read events for replay) and can be decided later.

### Protocol extension: 202 Accepted

When writ's policy evaluation can't produce a decision yet (e.g., awaiting
human approval), the response is HTTP 202 rather than 200 (permit) or
403 (deny).

**Response body:**

```json
{
  "message": "Visit https://writ.example.com/approve/abc123",
  "retryAfter": 5
}
```

- `message` — human-facing text displayed in the user's terminal
- `retryAfter` — seconds before the broker should try again

**Broker behavior:** no polling endpoint, no request tracking. The broker
goes back to the top of its existing cert request loop — including
re-authentication if the token has expired during the wait. Each retry is
a fresh, full cert request. The policy server evaluates current state each
time; if conditions are now met (approval granted), it returns 200.

```
loop:
  ensure valid token (re-auth if needed)
  request cert from CA
  case 200 → done, proceed with cert
  case 202 → show/update message, wait retryAfter, goto loop
  case 401 → clear token, goto loop
  case 403 → fail
```

The broker is smart about UX: repeated 202s with the same message keep a
spinner going rather than re-prompting. A new message replaces the old one.
User can Ctrl-C at any time.

**Why this design:**

- **Stateless evaluation.** The policy server doesn't track pending
  requests. First evaluation: "no approval exists → 202." Later: "approval
  exists → 200." No correlation needed.
- **Backwards compatible.** Old brokers that don't understand 202 treat it
  as an error. User retries manually. No break.
- **No new API surface.** Just a new status code and two fields.
- **Token expiry handled naturally.** Because the broker runs the full loop
  (including auth), a token that expires during a long approval wait is
  refreshed on the next iteration.

**Communication path:** the existing `userOutput io.Writer` in the broker's
`MatchWithUserOutput` stays live for the entire match flow. The broker
writes the 202 message to it, which flows through the gRPC stream to the
match command, which writes it to stderr. The match command and gRPC
protocol need no changes — they already handle streamed `UserOutput`
events.

**Changes required in epithet:**

1. Policy server protocol: define 202 response format
2. CA: pass 202 through (don't treat as error)
3. CA client (`pkg/caclient`): new response type for 202
4. Broker: new case in retry loop, spinner UX
5. Match command: no change

### Evaluation model: iterative with context enrichment

Policy evaluation isn't always a single pass. The model is:

1. Evaluate with available context (identity, connection details)
2. Result is permit, deny, or pending
3. On pending: the missing conditions (approval, oncall check, etc.)
   aren't known until evaluation — the policy itself determines what's
   needed
4. Broker retries; writ re-evaluates against updated state

This means the policy engine needs to natively understand obligations /
conditions — it can't just return permit/deny. The evaluation might
discover that an approval workflow is needed, that an oncall check must
pass, or that a time window hasn't opened yet.

## Domain model (sketch, not settled)

### Entities

- **Host** — a machine running sshd. Known by hostname. Has local accounts.
- **Local account** — a username on a specific host. Discovered by host
  agent, not created by writ.
- **Identity** — a person or service. Arrives via OIDC token. Writ doesn't
  manage identity lifecycle.

### Policy layer

Policy rules describe intent: who should be able to access what, under
what conditions. Two concerns:

1. **Matching** — does this rule apply to this request?
2. **Conditions** — what must be true? Some are instant (time, attributes),
   some are async (approval, oncall check).

### Events (tentative)

**Host inventory:**
- HostRegistered, HostRemoved
- LocalAccountDiscovered, LocalAccountRemoved

**Policy rules:**
- RuleCreated, RuleUpdated, RuleDeleted

**Workflow state:**
- ApprovalRequested, ApprovalGranted, ApprovalDenied, ApprovalExpired

**Audit (log-only, not projected into memory):**
- CertIssued, CertDenied

## Policy engine exploration

Evaluated three CNCF/industry options:

### OPA (Open Policy Agent) — CNCF Graduated

General-purpose policy engine, Rego language. Runs as a sidecar daemon.
Has partial evaluation (evaluate what you can, return residuals). The
residual concept maps to writ's "pending conditions" pattern. But
residuals are AST fragments, not typed obligations — OPA doesn't know
that a residual means "go ask a human."

### Cedar — CNCF Sandbox

Purpose-built authorization language from AWS. Embeddable library (Go via
cedar-go 1.0.0, Rust reference implementation). Permit/forbid model with
forbid-overrides-permit. Formally verified. Fast. But evaluation is purely
synchronous boolean — no concept of pending, obligations, or residuals.

Cedar policies map cleanly to writ's domain:

```
permit (
  principal in Team::"sre",
  action == Action::"ssh",
  resource in HostGroup::"production"
) when { resource.account == "root" && principal.oncall == true };
```

### OpenFGA — CNCF Incubating

Zanzibar-style relationship-based access control. Good for modeling
relationships (user → team → host-group → host). But it's a service with
its own storage — conflicts with event-sourced model (two sources of
truth).

### XACML (historical)

The one system that modeled obligations: PDP can return "Permit, but PEP
must do X first." Right concept, unusable implementation (XML-heavy, no
modern embeddable versions).

### Decision: Cedar with naming convention for obligations

Use cedar-go (unmodified, no fork) as the policy evaluation engine.
Obligations are handled via a naming convention on context keys combined
with Cedar's existing partial evaluation machinery.

**How it works:**

1. Writ policies are standard Cedar. Obligation-like conditions are
   ordinary Cedar `when` clauses referencing context keys with a naming
   convention (e.g., `context.require_approval`,
   `context.oncall_status`).

2. When evaluating a request, writ marks obligation context keys as Cedar
   `Variable` values (the partial eval "unknown" sentinel).

3. Cedar's partial evaluation runs: evaluates what it can (principal
   matching, host matching, attribute checks), leaves residual AST nodes
   for unresolved variables.

4. Writ inspects the residual AST to identify what's still needed:
   - Residual references `context.require_approval` → trigger approval
     workflow, return 202
   - Residual references `context.oncall_status` → check oncall API
     (fast, resolve inline)
   - No residuals → decision is fully determined (permit or deny)

5. For fast conditions: resolve inline, re-run Cedar with enriched
   context. For human-timescale conditions: return 202. On broker retry,
   if the approval now exists in writ's event log, the context is
   populated and Cedar evaluates to permit.

**Why this works:**

- No fork to maintain. cedar-go stays on upstream.
- Policy language is standard Cedar. No custom extensions.
- Partial eval already exists in cedar-go (`internal/eval/partial.go`,
  ~600 lines). Handles AST reduction, short-circuit evaluation, variable
  propagation.
- Clean separation: Cedar handles matching and boolean evaluation. Writ
  handles obligation semantics and workflow orchestration.

**cedar-go size** (~18,400 lines non-test):

- Eval engine: 2,725 lines
- Parser: 2,255 lines
- AST: 605 lines
- Partial eval: 592 lines
- Batch API: 402 lines
- Public API: 586 lines

Manageable codebase. Well-structured, inspectable, forkable if ever
needed (but shouldn't be).

**Language implication:** cedar-go at 1.0.0 nudges toward Go for writ.
Avoids FFI to the Rust Cedar reference implementation. Not locked in —
Rust Cedar would also work — but Go has the simpler integration path.
