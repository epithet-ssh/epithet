# Writ policy language — session 5: entity model and candidate syntaxes

Builds on `1.md`–`4.md`. Working notes, not commitments.

Goal of this session: make the policy language concrete enough to judge by
feel. One shared entity model, one shared scenario set, five candidate
languages rendered over identical scenarios — three declarative syntax
designs (A–C), plus the two other models toyed with along the way:
partial-eval logic programming (D) and full scripting (E). Pick by
reading, refine the winner next.

New constraints settled this session:

- **Users arrive via SCIM** (RFC 7643). The language's user vocabulary is
  exactly what SCIM can carry — no parallel identity model in writ.
- **Hosts register via writ's own API**, so the host object model is ours
  to design. Decision: k8s-style labels, not writ-managed groups and not
  hostname-convention encoding.
- **User matching = SCIM groups + a curated attribute set** (`department`,
  `userType`, `organization`). Not groups-only, not arbitrary attribute
  expressions.
- **Evaluation is order-independent.** File order never matters.

## Entity model (shared by all candidates)

### User

Provisioned and deprovisioned by the IdP via SCIM. Writ implements a SCIM
2.0 server endpoint (`/scim/v2/Users`, `/scim/v2/Groups`); the IdP pushes.
Writ never edits users.

SCIM → writ mapping:

| SCIM attribute | Writ treatment |
|---|---|
| `userName` | Identity key. Matched against the OIDC token identity (see binding note) |
| `emails[primary]` | Display and audit only |
| `active` | **Structural gate.** `active=false` → user matches nothing, ever. Not expressible (or bypassable) in policy |
| `groups` (via Group resources' `displayName`) | Matchable — the primary vocabulary |
| `userType` | Matchable (`employee`, `contractor` — whatever the IdP sends) |
| Enterprise ext `department` | Matchable |
| Enterprise ext `organization` | Matchable |
| Enterprise ext `manager` | Stored, **obligation-only** (feeds `require manager-approval`); never matchable |
| `displayName`, `name.*` | Display and audit only |
| Enterprise ext `employeeNumber`, `costCenter` | Stored for audit, unmatchable |
| `roles`, `entitlements` | Ignored in v1 — free-form and wildly IdP-inconsistent; revisit if a real deployment needs them |
| Everything else (`phoneNumbers`, `photos`, `addresses`, ...) | Ignored |

**Identity binding (OIDC ↔ SCIM).** The cert request carries an OIDC
token; the SCIM store carries users. **Identity is an opaque string to
writ** — one configured claim from the token (default `email`, could be
`sub` or anything else the deployment picks) is compared byte-for-byte
against one configured SCIM attribute (default `userName`). Writ never
parses or interprets the value; it is frequently email-shaped, but that
is the IdP's convention, not writ's model. No match → 403, user does not
exist as far as writ is concerned. This makes SCIM deprovisioning the
kill switch: IdP sets `active=false` or deletes the user, and no policy
text can grant them anything.

**Group name caveat.** Policy references SCIM Group `displayName`, which
RFC 7643 does not require to be unique. Writ warns loudly on duplicate
displayNames at sync time and treats a policy reference to a duplicated
name as matching the union (with the warning pointing at the IdP as the
thing to fix).

### Host

Registered via writ's API. Shape:

```
Host {
  name      string              // unique, stable identifier
  labels    map[string]string   // env=prod, role=db, region=us-east, ...
  accounts  []Account           // reported by host agent, not declared
  lastSeen  timestamp           // last agent report
}
```

API sketch (grounding, not a full spec):

```
PUT    /api/v1/hosts/{name}            {"labels": {"env":"prod","role":"db"}}
DELETE /api/v1/hosts/{name}
POST   /api/v1/hosts/{name}/accounts   [{"name":"ubuntu","uid":1000,"system":false}, ...]
```

- Registration is idempotent upsert; labels are replaced, not merged.
- The accounts report is a full replacement of the host's account
  inventory (agent-side diffing is an optimization, not semantics).
- All of these become events (`HostRegistered`, `HostLabelsChanged`,
  `AccountDiscovered`, `AccountRemoved`, ...) per the 2.md event model.
- How the agent authenticates to this API is deliberately out of scope
  here (future: host certs / NADIR bootstrap).

Staleness: a host past a report deadline gets flagged in writ's UI/CLI.
Whether staleness blocks issuance is a deployment knob, default off —
the inventory is a mirror of reality, and reality doesn't stop being real
when a cron job dies. Revisit if operators want fail-closed staleness.

### Account and principal

An account is `{host, name}`, discovered by the host agent. The principal
writ certifies is exactly one `account@host` — the narrow-principal model
from 1.md.

**Evaluation is inventory-grounded.** Account match expressions in policy
(including `*`) match against the host's *reported* inventory. A request
for an account the host has never reported is denied even if a rule's
pattern would match the string — writ refuses to certify access to an
account it has no evidence exists. This is what `account *` from the 3.md
sketch always meant ("any account the host reports"); v1 makes it uniform
for literal and glob matches too.

### Request

Unchanged from the epithet policy protocol: OIDC token + connection block
(`remoteHost`, `remoteUser`, `port`, ...). Writ resolves `remoteHost` →
Host, `remoteUser` → account name, token → User, then evaluates.

### Requirements (async facts / obligations)

Per 4.md: named handlers in writ's registry. Policy only names them; the
handler declares latency class (`fast` | `human`) and side-effect-ness.

v1 registry:

| Name | Latency | Side effects | Meaning |
|---|---|---|---|
| `oncall` | fast | no | requesting user is on the oncall rotation (integration) |
| `mfa` | fast | no | recent MFA verification exists for this user |
| `approval` | human | yes | an unexpired approval for this request exists; else create `ApprovalRequested`, return 202 |
| `manager-approval` | human | yes | as `approval`, but the approver is resolved from the SCIM `manager` chain |

`require` is only legal on allow rules and can only withhold permission —
monotonicity by construction (the 4.md soundness argument).

**Handlers are pluggable; parameterization lives at registration, not in
the grammar.** Deployments will want requirements nobody can guess
(`ticket-open`, `change-window-approved`, `training-current`), so
handlers follow epithet's auth-plugin precedent: CGI-ish subprocess
exec'd per check, JSON on stdin, JSON on stdout. The three-state fact
model *is* the plugin protocol:

```
stdin:  { "requirement": "sre-approval",
          "config":  { ... },                    // static, from registration
          "request": { "user": {"id":..., "groups":[...], "type":..., "dept":..., "org":...},
                       "host": {"name":..., "labels":{...}},
                       "account": "root",
                       "connection": { ... } },
          "rule":    { "label": "sre-prod-root" } }

stdout: { "status": "satisfied", "expires": "2026-08-05T21:07:00Z" }
     |  { "status": "unsatisfied", "message": "not on the SRE rotation" }   → feeds 403
     |  { "status": "pending",
          "message": "approval requested — https://writ.example.com/a/x1",
          "retryAfter": 5 }                                                 → feeds 202
```

`expires` lets a settled fact be cached ("oncall=true, good for 60s").
Latency class and side-effect-ness remain registration properties — writ
needs them *before* first invocation to order evaluation (fast facts
before human ones, per the cross-rule laziness rule).

A requirement name in policy is a **configured instance**: handler
binary + static config bound to a name in writ's config.

```
[requirement "sre-approval"]
exec         = "writ-approval"
latency      = "human"
side-effects = true
config       = { approvers = "group:SRE", count = 1 }

[requirement "dba-oncall"]
exec         = "writ-pagerduty"
latency      = "fast"
config       = { rotation = "dba-primary" }
```

Policy says `require [dba-oncall, sre-approval]` — names only, no
argument syntax. Why registration-side parameters win over
`require approval(from="SRE")` in the grammar:

1. **Fact identity stays trivial.** Dedup cache, in-flight coalescing,
   approval correlation, and audit events key on
   `(requirement-name, request)`. Grammar args would make identity
   "(name + canonicalized argument set)" — two rules with slightly
   different args become different facts, approvals stop being shareable
   across rules, and the 4.md dedup machinery grows a canonicalization
   problem.
2. **Auditability.** `sre-approval` in a 202 message, an audit event, or
   a grep means one thing, defined in one place. A parameterized
   requirement means something different in every rule that uses it.
3. **Per-rule variation mostly dissolves into context.** Parameters that
   genuinely vary per-rule usually correlate with the matched entities,
   and handlers see full context — "approvers = the owning team" is not
   `approval(team=X)` in fifty rules but one `owner-approval` instance
   whose handler reads `host.labels["team"]`.

Cost accepted: many variants → many registry entries
(`approval-1p`, `approval-2p`, ...). At realistic scales that
explicitness is a feature. And `require name(k=v)` remains addable later
at zero compatibility cost — `(` after a requirement name is a syntax
error today, so the door stays open without reserving anything.

One boundary to respect: handlers that need *writ's own* durable state
(the approval workflow creates `ApprovalRequested` events and hosts the
approval UI) are built-ins, not plugins — plugins integrate external
systems and own their state there (the ticket tracker, the oncall
service). If plugins ever need writ-side state, that's a deliberate API
to design, not something to back into.

### Sync state flags (`when` conditions) — new in this session

The freeze scenario exposed a gap: "deny during a freeze" cannot be an
async fact. An unresolved fact defaults false; a deny gated on it would
*fail open* — exactly the non-monotone form 4.md proved unsound.

So the language has two condition kinds, and the split is load-bearing:

- **`require <fact>`** — async-capable, three-state, allow-only. Unmet →
  pending → 202. Only ever withholds.
- **`when <flag>`** — references a **named boolean flag in writ's own
  projected state**, set and cleared via API/CLI/events
  (`FlagSet{"freeze"}`, `FlagCleared{"freeze"}`). Synchronous, two-state,
  known at evaluation time, never 202s. Legal on both allow and deny.

A deny with `when` is sound because the flag is local state — there is no
"unresolved" to fail open through. Flags are writ's mechanism for freeze
windows, maintenance modes, and incident lockdowns; integrations can
drive them (a cron flips `business-hours`, an incident bot flips
`lockdown`) without the evaluator ever waiting on anything.

### Grants vs. rules

Two layers with the same match vocabulary:

- **Rules** — durable, authored policy text. Applied atomically via
  `writ policy apply <file>`, stored as a `PolicyUpdated` event carrying
  the full text (versioned history for free; the file on disk is the
  working copy, the event log is the record).
- **Grants** — time-boxed, individual, operational. First-class events
  (`GrantCreated`, `GrantRevoked`, `GrantExpired`), created via CLI/API,
  never by editing policy text:

  ```
  writ grant carol@example.com postgres@prod-db-1 \
      --require approval --ttl 4h --reason "incident #1234"
  ```

  A grant evaluates as one more allow rule unioned with the authored set.
  Expiry is enforced by the evaluator (grant past `expires` simply doesn't
  match); `GrantExpired` is bookkeeping, not enforcement.

Rationale: 3.md's sketch put `expire 4h` in policy text, but "4h from
when? From authoring? From apply?" has no good answer in a declarative
file, and short-lived grants churning through policy diffs pollutes
review history. Authored rules keep an absolute `until <timestamp>` form
for planned temporary policy (migration windows); relative TTLs belong to
grants, where creation time is an event fact.

## Evaluation semantics (shared by all candidates)

Order-independent. For a request `(user, host, account)`:

1. **Structural gates.** User resolves via identity binding and is
   `active`; host is registered; account is in the host's inventory.
   Any failure → 403.
2. **Collect matching rules** — authored rules plus unexpired grants.
   A rule matches if its user, host, and account expressions all match.
3. **Deny wins.** Any matching deny whose `when` flags (if any) currently
   hold → 403. Always. No allow can override.
4. **Allow, sync conditions first.** Matching allows whose `when`/`until`
   conditions fail drop out — they are non-matches, not pending.
5. **Allow, async requirements.** Surviving allows evaluate their
   `require` facts through the three-state resolver (4.md). If any single
   allow has all requirements settled-true → **200**.
6. **Pending.** Else, if any surviving allow has requirements unstarted
   or pending → **202** with `retryAfter` and a human message naming what
   is being waited on.
7. Else → **403**.

Cross-rule laziness (extends 4.md's per-rule laziness): fast facts for
all surviving allows resolve first; human-latency, side-effecting facts
(`approval`) are triggered only for allows whose fast requirements have
all settled true. An approval request is only ever created when it is the
*last* thing standing between the user and a cert — no paging a human for
a rule whose oncall check was already false.

Evaluator errors (handler crash, integration timeout past deadline) fail
closed: 500, never "treat as non-match" (4.md invariant).

Cert parameters: writ carries deployment-level defaults (ttl, extensions);
a rule may override ttl. If multiple satisfied allows specify different
ttls, take the maximum — each rule alone would have granted that ttl, and
order-independence forbids "first rule wins." (Flagged as an open
question below; minimum is the conservative alternative.)

## Scenario set

Eight scenarios, rendered identically in every candidate:

- **S1** Baseline: SRE group → `ubuntu` on `env=prod`.
- **S2** Elevated: SRE group → `root` on `env=prod`, oncall + approval.
- **S3** Individual time-boxed: carol → `postgres` on `prod-db-1`,
  approval-gated, 4 hours.
- **S4** Attribute guard: contractors get nothing on `env=prod`.
- **S5** Dev wildcard: Engineering group → any account on `env=dev`.
- **S6** Breakglass: Security Oncall group → `root` anywhere, MFA-gated,
  security channel notified on use.
- **S7** Compound selector: DBA group → `postgres` on
  `role=db, env=staging`.
- **S8** Freeze: during the `freeze` flag, nobody but Infrastructure
  touches `env=prod`.

S6 introduces one small clause beyond the settled model: `notify <target>`
— a fire-and-forget side effect on issuance that never gates the
decision. Every issuance is audited regardless; `notify` is for the
"wake someone up when this rule fires" cases. It rides along in all three
candidates as a test of how each syntax absorbs growth.

## Candidate A — pf-inspired keyword rules

Evolution of the 3.md sketch. Macros bind names to match expressions;
rules are keyword-introduced clauses reading roughly as sentences.

```
# ── macros ──────────────────────────────────────────────
sre   = user group "SRE"
eng   = user group "Engineering"
dba   = user group "DBA"
sec   = user group "Security Oncall"
infra = user group "Infrastructure"

prod  = host env=prod
dev   = host env=dev

# ── rules ───────────────────────────────────────────────

# S1 — baseline
allow user sre host prod account ubuntu

# S2 — elevated
allow user sre host prod account root \
    require oncall, approval \
    label "sre-prod-root"

# S3 — authored form (grants CLI is the preferred path)
allow user "carol@example.com" host "prod-db-1" account postgres \
    require approval \
    until 2026-08-05T22:00Z

# S4 — attribute guard
deny user type "contractor" host prod

# S5 — dev wildcard
allow user eng host dev account *

# S6 — breakglass
allow user sec host * account root \
    require mfa \
    notify "security-alerts"

# S7 — compound selector
allow user dba host role=db env=staging account postgres

# S8 — freeze
deny user !infra host prod when freeze
```

Grammar sketch (EBNF-ish):

```
file      = { macro | rule } ;
macro     = ident "=" ( "user" user-expr | "host" host-expr | "account" acct-expr ) ;
rule      = ( "allow" | "deny" ) clause { clause } ;
clause    = "user" user-expr | "host" host-expr | "account" acct-expr
          | "require" name { "," name }          (* allow only *)
          | "when" name { "," name }
          | "until" timestamp                    (* allow only *)
          | "ttl" duration                       (* allow only *)
          | "notify" string { "," string }
          | "label" string ;
user-expr = [ "!" ] ( ident                      (* macro ref *)
          | "group" string | "type" string | "dept" string | "org" string
          | string                               (* literal identity *)
          | "*"
          | "{" user-expr { "," user-expr } "}" ) ;   (* union *)
host-expr = [ "!" ] ( ident | selector { selector } | string | "*"
          | "{" host-expr { "," host-expr } "}" ) ;
selector  = key "=" value ;                      (* multiple = AND *)
acct-expr = ident | string | "*" | "{" acct-expr { "," acct-expr } "}" ;
```

Notes:

- Omitted `user`/`host`/`account` clause = `*` (pf convention).
- `#` comments, `\` line continuation, order of clauses within a rule is
  free.
- Braces are union; juxtaposed label selectors are AND. Intersection
  across user expressions is deliberately absent — carve-outs are deny
  rules, which is the pf philosophy and keeps expressions flat.
- `!` negation on match expressions exists primarily for deny carve-outs
  (S8). Legal on allow too, but style guidance says prefer a deny.
- `label "name"` (pf's own device) gives a rule a stable name for audit
  events and 202 messages, without making names mandatory.

**Feel.** Reads aloud well ("allow user sre on host prod as account
root, requiring oncall and approval"). Macros carry the weight at scale —
500 rules over a good macro vocabulary reads like a routing table.
Weaknesses: clause soup on long lines (continuations required), names are
opt-in so audit references degrade to file:line for unlabeled rules, and
a custom grammar means writ owns lexer/parser/formatter/highlighting.

## Candidate B — named structured blocks (HCL-shaped)

Every rule is a named block. No macro layer — labels on hosts and groups
in the IdP already name the sets; the rule name names the intent.

```hcl
# S1 — baseline
rule "sre-prod-ubuntu" {
  users    { group = "SRE" }
  hosts    { labels = { env = "prod" } }
  accounts = ["ubuntu"]
}

# S2 — elevated
rule "sre-prod-root" {
  users    { group = "SRE" }
  hosts    { labels = { env = "prod" } }
  accounts = ["root"]
  require  = ["oncall", "approval"]
}

# S3 — authored form (grants CLI is the preferred path)
rule "carol-prod-db-incident-1234" {
  users    { id = "carol@example.com" }
  hosts    { name = "prod-db-1" }
  accounts = ["postgres"]
  require  = ["approval"]
  until    = "2026-08-05T22:00:00Z"
}

# S4 — attribute guard
rule "no-contractors-in-prod" {
  effect = "deny"
  users  { type = "contractor" }
  hosts  { labels = { env = "prod" } }
}

# S5 — dev wildcard
rule "eng-dev-anything" {
  users { group = "Engineering" }
  hosts { labels = { env = "dev" } }
}

# S6 — breakglass
rule "security-breakglass" {
  users    { group = "Security Oncall" }
  accounts = ["root"]
  require  = ["mfa"]
  notify   = ["security-alerts"]
}

# S7 — compound selector
rule "dba-staging-db" {
  users    { group = "DBA" }
  hosts    { labels = { env = "staging", role = "db" } }
  accounts = ["postgres"]
}

# S8 — freeze
rule "prod-freeze" {
  effect = "deny"
  users  { except { group = "Infrastructure" } }
  hosts  { labels = { env = "prod" } }
  when   = ["freeze"]
}
```

Structure notes:

- `effect` defaults to `"allow"`; omitted `users`/`hosts`/`accounts`
  blocks mean any (subject to inventory grounding).
- `users`/`hosts` blocks: multiple attributes inside one block AND
  together; repeat the block for union. `except { ... }` subtracts.
- Rule names are mandatory and unique — every audit event, 202 message,
  and grep lands on a name.
- Parsing is off-the-shelf (`hashicorp/hcl`); formatter, highlighting,
  and editor support come free. A JSON mapping exists by construction,
  which matters for storing rules as events and for a future UI that
  round-trips policy.

**Feel.** Boring in the good way and the bad way. Diffs and code review
are excellent — a change touches one named block. Nothing reads as a
sentence; the 500-rule file is 3000+ lines of block scaffolding; and
without a macro layer, recurring user-set/host-set combinations repeat
in full (mitigable with HCL locals/variables, but each such addition
drags more HCL semantics into the policy surface).

## Candidate C — SSH-native arrow notation

Leans on the `account@host` mental model every SSH operator already has.
A rule is `who -> account@where`, with requirements after `?` and
trailing `key:value` clauses.

```
# ── macros ──────────────────────────────────────────────
sre   = group:SRE
eng   = group:Engineering
dba   = group:DBA
sec   = group:"Security Oncall"
infra = group:Infrastructure
prod  = {env=prod}

# ── rules ───────────────────────────────────────────────

# S1 — baseline
$sre -> ubuntu@$prod

# S2 — elevated
$sre -> root@$prod ? oncall, approval

# S3 — authored form (grants CLI is the preferred path)
id:"carol@example.com" -> postgres@prod-db-1 ? approval until:2026-08-05T22:00Z

# S4 — attribute guard
deny type:contractor -> *@$prod

# S5 — dev wildcard
$eng -> *@{env=dev}

# S6 — breakglass
$sec -> root@* ? mfa notify:security-alerts

# S7 — compound selector
$dba -> postgres@{env=staging,role=db}

# S8 — freeze
deny !$infra -> *@$prod when:freeze
```

Grammar sketch:

```
rule      = [ "deny" ] user-sel "->" acct "@" host-sel [ "?" reqs ] { clause } ;
user-sel  = [ "!" ] ( "$" ident | tag ":" value | "*"
          | "(" user-sel { "|" user-sel } ")" ) ;
tag       = "id" | "group" | "type" | "dept" | "org" ;
host-sel  = "$" ident | "{" key "=" val { "," key "=" val } "}"   (* AND *)
          | name-glob | "*" ;
reqs      = name { "," name } ;
clause    = ( "when" | "until" | "ttl" | "notify" | "label" ) ":" value ;
```

Notes:

- User identity is an opaque identifier to writ (whatever the IdP puts
  in SCIM `userName` — often email-shaped, never email-semantic), so
  individual users appear as `id:"..."`, tagged and quoted like every
  other attribute match. A consequence worth noting: an unquoted `@`
  occurs in exactly one place in a rule — the head's `account@host`
  separator — so the lexer needs no positional tricks.
- Macro references take `$` so bare words stay unambiguous.
- `deny` is a keyword prefix; a bare `!` sigil for deny was considered
  and rejected as too cryptic against `!` already meaning match negation.
- One line per rule is the norm; continuations exist but the syntax
  visibly resists clause growth.

**Feel.** The 8-scenario file is the shortest and the most instantly
legible of the three — `$sre -> root@$prod ? oncall, approval` is close
to how you'd say it out loud. The costs show up at the edges: sigil
density (`$ : ! ? @ {}`) approaches line noise for newcomers, trailing
`key:value` clauses get cramped as rules grow options, and like A it's a
custom grammar writ must own tooling for — with a trickier lexer than
A's keyword grammar.

## Candidate C′ — head/tail hybrid (iteration in progress)

Feedback on a first read-through of A vs C: A's flat keyword grammar is
tricky in exactly the way pf.conf is tricky — `allow user sre host prod
account ubuntu` is six undifferentiated words whose grouping
`(allow (user sre) (host prod) (account ubuntu))` exists only in the
reader's head. The structure is carried by juxtaposition and implicit
keyword pairing. C's sigils, line-noise aesthetics aside, carry the
parse tree in the line's visible shape: `$sre -> root@$prod` cannot be
mis-grouped.

The general principle: keyword grammars read aloud well but scan badly —
their failure mode is a silent re-grouping. Punctuation grammars read
aloud badly but scan instantly — their failure mode is visibly malformed.
Policy files are scanned far more often than read aloud, and a mis-scan
of an access rule is a security event.

But C's weakness was its *tail*: `? oncall, approval until:... notify:...`
gets cramped as clauses accumulate — and the tail is exactly where A's
keyword style works, because tail clauses are keyword-labeled like CLI
flags, each self-announcing. Hence the hybrid: **C's punctuation head
(who `->` account `@` where), A's keyword clauses for the tail**, with
commas separating tail clauses so boundaries stay visible there too.

The `?` sigil drops (keyword `require` absorbs it). Two tail variants
were rendered during iteration — comma-separated `keyword value` clauses
with lists by keyword repetition, vs. lists in braces — and both lost to
a third option that fell out of noticing the sigil budget was being
spent unsystematically:

**`[]` means list, `{}` means label-selector match. Always.**

Each sigil has exactly one meaning, and the shapes match their JSON/YAML
counterparts (`{env=prod}` is a map — it matches labels; `[oncall,
approval]` is an array). No overloading, no position-dependent reading.
And once `[]` exists it generalizes to the head for free: a bracketed
list is a union in any match position.

```
# ── macros ──────────────────────────────────────────────
sre   = group:SRE
eng   = group:Engineering
dba   = group:DBA
sec   = group:"Security Oncall"
infra = group:Infrastructure
prod  = {env=prod}

# S1 — baseline
$sre -> ubuntu@$prod

# S2 — elevated
$sre -> root@$prod  require [oncall, approval], label "sre-prod-root"

# S3 — authored form (grants CLI is the preferred path)
id:"carol@example.com" -> postgres@prod-db-1  require approval, until 2026-08-05T22:00Z

# S4 — attribute guard
deny type:contractor -> *@$prod

# S5 — dev wildcard
$eng -> *@{env=dev}

# S6 — breakglass
$sec -> root@*  require mfa, notify "security-alerts"

# S7 — compound selector
$dba -> postgres@{env=staging,role=db}

# S8 — freeze
deny !$infra -> *@$prod  when freeze

# stress test — worst-case clause pileup
$sre -> root@{env=prod,role=db} \
    require [oncall, approval, mfa], \
    ttl 2m, notify "security-alerts", label "db-root-breakglass"

# head unions, same sigil, same meaning
[$sre, $dba] -> [ubuntu, deploy]@$prod
```

Grammar sketch:

```
rule      = [ "deny" ] head [ tail ] ;
head      = user-sel "->" acct-sel "@" host-sel ;
tail      = clause { "," clause } ;
clause    = keyword ( value | list ) ;
keyword   = "require" | "when" | "until" | "ttl" | "notify" | "label" ;
list      = "[" item { "," item } "]" ;
user-sel  = [ "!" ] ( "$" ident | tag ":" value | "*" | list ) ;
tag       = "id" | "group" | "type" | "dept" | "org" ;
acct-sel  = name | glob | "*" | list ;
host-sel  = "$" ident | "{" key "=" val { "," key "=" val } "}"   (* AND *)
          | name-glob | "*" | list ;
```

Singleton lists may omit brackets (`require approval` ≡
`require [approval]`).

**Noted asymmetry, judged acceptable:** `[]` reads as *any-of* in match
positions (`[ubuntu, deploy]@` — either account) but *all-of* in
`require [oncall, approval]` — every gate. English carries the same
asymmetry ("as ubuntu or deploy", "require oncall and approval"), and
the clause semantics force the right reading; but it is an asymmetry,
recorded here so it's a decision rather than an accident.

## Candidate D — Datalog (partial-eval logic programming)

Policy as Horn clauses over the entity model. Not full Prolog: Datalog —
no function symbols, no recursion surprises, guaranteed termination,
decidable. That cut is what makes logic programming safe to hand to a
policy engine. Engine options: Google's Mangle (Go, maintained), or a
small custom resolver — at writ's scale (thousands of facts) nothing
sophisticated is needed, not even tabling.

Writ's projections *are* an extensional database already: `group(U, G)`,
`label(H, K, V)`, `user_type(U, T)`, `account(H, A)`, `flag(F)` are just
the SCIM sync and host inventory viewed as relations. Async facts
(`oncall(U)`, `approved(U, A, H)`, `mfa(U)`) are three-state extensional
predicates backed by the 4.md resolver. Partial evaluation is native
here: a proof attempt that gets stuck on an unresolved async predicate
returns that goal as the residual — **the residual goal literally is the
obligation.** This is the idea XACML fumbled and Cedar lacked, expressed
in the formalism where it's a one-liner.

```prolog
% ── intermediate predicates (the macro layer, but richer) ──
sre(U)   :- group(U, "SRE").
eng(U)   :- group(U, "Engineering").
dba(U)   :- group(U, "DBA").
sec(U)   :- group(U, "Security Oncall").
infra(U) :- group(U, "Infrastructure").
prod(H)  :- label(H, env, prod).
dev(H)   :- label(H, env, dev).

% S1 — baseline
allow(U, ubuntu, H) :- sre(U), prod(H).

% S2 — elevated
allow(U, root, H) :- sre(U), prod(H), oncall(U), approved(U, root, H).

% S3 — authored form (grants CLI is the preferred path)
allow("carol@example.com", postgres, "prod-db-1") :-
    approved("carol@example.com", postgres, "prod-db-1"),
    before(now, "2026-08-05T22:00Z").

% S4 — attribute guard
deny(U, _, H) :- user_type(U, "contractor"), prod(H).

% S5 — dev wildcard
allow(U, _, H) :- eng(U), dev(H).

% S6 — breakglass
allow(U, root, _) :- sec(U), mfa(U).
notify("security-alerts") :- fired(allow, U, root, H), sec(U).

% S7 — compound selector
allow(U, postgres, H) :- dba(U), label(H, env, staging), label(H, role, db).

% S8 — freeze
deny(U, _, H) :- prod(H), flag(freeze), not infra(U).
```

The decision procedure lives in the engine, not the clauses:
`permit(U, A, H)` iff `allow(U, A, H)` is provable and `deny(U, A, H)` is
not. Deny-wins is engine semantics, exactly as in A–C.

What the settled design decisions look like from inside Datalog — this
is the striking part:

- **Order-independence is native.** Datalog has set semantics; clause
  order has never meant anything. The evaluation model chosen this
  session is the one logic programming has always had.
- **Monotonicity is a theorem.** Pure positive Datalog is monotone —
  adding facts can only grow the derivable set. The 4.md invariant
  ("resolving a fact false→true only widens access") is the classic
  textbook property, not something to engineer.
- **The `require`/`when` split is a stratification rule.** Negation
  (`not infra(U)`) is where monotonicity breaks, so the loader enforces:
  `not` may only be applied to synchronous predicates (projections and
  flags), never to async ones, and async predicates may appear only
  positively and only in `allow` bodies. Trivial static check over the
  clause ASTs — same strength as the Cedar JSON-AST lint from 4.md, but
  actually trivial.
- **Reverse queries come free.** `allow(U, root, "prod-db-1")?` with `U`
  unbound enumerates who can reach root there; `allow("carol@...", A, H)?`
  enumerates everything carol can reach. Access reviews (SOC 2, customer
  audits) are queries, not a separate enumeration subsystem.

Weak spots, honestly: `notify` is clumsy (needs a feedback predicate or
annotation bolt-on — decision logic is Datalog's home turf, side-band
actions are not); rule naming for audit needs annotations too; and the
authoring surface is the real problem. `:-`, unification variables, and
negation-as-failure are a paradigm shift for an audience that knows
pf.conf and sudoers. Reading is learnable; writing confidently — knowing
that `deny(U, _, H)` with an anonymous variable means *any* account — is
where non-PL operators get hurt.

**Feel.** For anyone fluent in logic programming this is the most
*correct*-feeling candidate: the domain is relations and derivation
rules, and here the language admits it. The macro layer (intermediate
predicates) is strictly more powerful than A's macros. But it optimizes
for the wrong reader — writ's operators are ops engineers, not PL
people, and "the policy language requires a paradigm shift" is the same
adoption argument that killed Cedar in 4.md, with a steeper shift.

## Candidate E — full Lua

The other pole: no language design at all. Policy is a Lua script; writ
(via gopher-lua, sandboxed, instruction-budgeted, no I/O) calls
`evaluate(request)` per request.

Rendered in the *disciplined* style — requirements returned as data so
the engine keeps running the 202 loop:

```lua
function evaluate(req)
  local u, h, a = req.user, req.host, req.account

  -- S8 — freeze (denies must come first: ordering is on the author)
  if writ.flag("freeze") and h.labels.env == "prod"
      and not u:in_group("Infrastructure") then
    return deny("prod is frozen")
  end

  -- S4 — attribute guard
  if u.type == "contractor" and h.labels.env == "prod" then
    return deny("contractors have no prod access")
  end

  -- S1 — baseline
  if u:in_group("SRE") and h.labels.env == "prod" and a == "ubuntu" then
    return allow()
  end

  -- S2 — elevated
  if u:in_group("SRE") and h.labels.env == "prod" and a == "root" then
    return allow{ require = {"oncall", "approval"} }
  end

  -- S3 — authored form (grants CLI is the preferred path)
  if u.id == "carol@example.com" and h.name == "prod-db-1"
      and a == "postgres"
      and writ.now() < writ.time("2026-08-05T22:00Z") then
    return allow{ require = {"approval"} }
  end

  -- S5 — dev wildcard
  if u:in_group("Engineering") and h.labels.env == "dev" then
    return allow()
  end

  -- S6 — breakglass
  if u:in_group("Security Oncall") and a == "root" then
    return allow{ require = {"mfa"}, notify = {"security-alerts"} }
  end

  -- S7 — compound selector
  if u:in_group("DBA") and a == "postgres"
      and h.labels.env == "staging" and h.labels.role == "db" then
    return allow()
  end

  return deny("no rule matched")
end
```

What it buys: zero grammar/parser/formatter work; unlimited
expressiveness for the org rule too weird for any DSL; the best
debugging story of all five (`print`, unit tests in plain Lua); helpers
and loops when policies get genuinely repetitive.

What it costs — and this is the structural problem, not a style quibble:
**every invariant sessions 2–4 established becomes a convention.**

- *Order-independence*: gone. First `return` wins; S8's deny is only
  deny-wins because the author placed it first. The evaluation model
  chosen this session is unimplementable over an opaque function.
- *Monotonicity*: gone as a guarantee. The disciplined style above is
  monotone, but `if not writ.check("high_risk") then return allow() end`
  — the exact fail-open form 4.md proved unsound — is three lines away,
  and no static check over a Turing-complete script will catch it.
- *Deny-wins, fail-closed, laziness ordering*: all reconstructible, all
  by author discipline, none by construction.
- *Reverse queries / analyzability*: none, except brute-force
  enumeration of an opaque function.

And notice what the disciplined rendering above actually looks like:
candidate B with `if`/`then` noise around every block. Lua adds value
over the DSLs only when you use its power — and using the power is
precisely what dissolves the guarantees. The escape hatch and the
foot-gun are the same hatch.

**Where Lua genuinely belongs: the requirement-handler registry.** The
4.md design already puts latency class and side effects in handlers,
outside the language. Making *handlers* scriptable — `require
ticket-open` backed by a deployment-local Lua script with a sandboxed
HTTP+JSON API — gives every deployment its own conditions without
recompiling writ, while the policy surface stays declarative and the
invariants stay structural. Power users get Lua; the policy file never
sees it.

| Reads at 500 rules | **good (macros)** | poor (scaffolding) | fine until clauses pile up | good (set semantics, predicates) | it's a program now |
| Diff / review ergonomics | good | **best** (named blocks) | good | good | poor (imperative) |

| Order-independence | engine-enforced | engine-enforced | engine-enforced | **native** | **lost** |
| Monotonicity | by construction | by construction | by construction | theorem + trivial lint | **by discipline only** |

### Recommendation

**Candidate C′ — the head/tail hybrid — is the recommendation**, reached
by iteration rather than by the original comparison: A's keyword grammar
failed the scan test (implicit pairing — the sexp grouping exists only
in the reader's head), C's punctuation head survived contact, and C's
cramped tail was replaced with A's keyword clauses, comma-separated,
with `[]`/`{}` given single fixed meanings. B contributes its one
structural win as a lint-level nudge: `label` on any rule carrying
`require`, `when`, or `notify` — rules that show up in 202 messages and
pages deserve stable names.

Reasoning: the 500-rule file is the design target, not the 8-rule demo —
writ exists for shops that outgrew epithet's built-in policy. C′ keeps
the macro layer that makes that file legible, puts the dangerous part of
every rule (who/what/where) into punctuation that cannot be silently
mis-grouped, and keeps a keyword tail that absorbs new clauses (`ttl`,
`notify`, future `port`?) without strain. B optimizes for the machine
and the reviewer at the cost of the author and reader.

**D is the strongest challenger, and loses only on the audience.** The
comparison table's middle rows say it plainly: everything sessions 2–4
fought for — order-independence, monotonicity, obligations-as-residuals
— Datalog has natively, as sixty-year-old theorems rather than design
work. But the adoption argument that killed Cedar in 4.md applies with
more force: writ's operators know pf.conf and sudoers, and `:-` with
unification variables is a bigger ask than Cedar was. The right use of D
is underneath: **A's rule IR compiles to Datalog clauses trivially**
(each rule one clause, macros as intermediate predicates), so if reverse
queries graduate from nice-to-have to product requirement — access
reviews will push exactly there — writ can grow a Datalog evaluation
backend without the policy file changing shape. Worth noting: brute-force
enumeration (all users × one evaluation) also answers reverse queries at
writ's scale; D makes them elegant, not merely possible.

**E is rejected as a policy surface but adopted as a direction for the
handler registry.** A policy file in Lua dissolves every structural
guarantee into author discipline, and its disciplined style collapses
into candidate B with extra noise. But deployment-local requirement
handlers in sandboxed Lua (`require ticket-open` backed by a script)
extend writ where extension belongs — behind named facts, outside the
language, invariants intact.

The evaluator is shared regardless — A/B/C/C′ are frontends over the
same rule IR (and D can be a backend for it), so the surface choice
stays reversible until real policies accumulate.

## The IL is the target; the language is a frontend

Settled framing, and it inverts the usual relationship: **writ's real
policy interface is the intermediate language.** The surface syntax (C′)
is one frontend — the human-optimized one — over a rule IL that is the
actual contract. Grants already are IL-native (the CLI constructs rules,
no text involved); a future web UI would be another IL producer; the
Datalog backend, if it ever materializes, is an IL consumer. Forms and
interfaces can be experimented with freely because none of them are the
system of record's format.

Sketch of a rule in IL (JSON-shaped because the event log and any UI
want that; the Go structs are the real definition):

```json
{
  "label": "sre-prod-root",
  "effect": "allow",
  "users":    [ {"group": "SRE"} ],
  "accounts": [ {"name": "root"} ],
  "hosts":    [ {"labels": {"env": "prod"}} ],
  "require":  ["oncall", "approval"],
  "when":     [],
  "until":    null,
  "ttl":      null,
  "notify":   []
}
```

- Each of `users`/`accounts`/`hosts` is a disjunction of matchers
  (`[]` = the surface language's union lists); matcher kinds are the
  tagged forms (`id`/`group`/`type`/`dept`/`org`, `labels`/`name-glob`,
  `name`/`glob`), each with an optional negation flag.
- **Macros are expanded at compile time.** The IL is self-contained; the
  `PolicyUpdated` event stores both the source text (for humans and
  provenance) and the compiled IL (for the evaluator). Nothing
  downstream of the compiler knows macros existed.
- The IL needs a schema version from day one — it outlives any surface
  syntax revision by design.

### Authoring tooling (roadmap, not v1)

A tree-sitter grammar and an LSP server for the surface syntax. The
tree-sitter grammar is table stakes (highlighting, structural editing,
and it doubles as a second implementation keeping the grammar honest).
The LSP is where writ has an unfair advantage: because writ owns the
inventory, its language server can lint policy against *reality*, not
just syntax —

- `group:SRE` — warn if no SCIM group by that displayName exists
- `{env=prod,role=bd}` — "no registered host currently matches this
  selector — typo for role=db?"
- `require aproval` — unknown requirement handler
- hover on `$prod` — expansion plus "currently matches 47 hosts"

Static policy languages can't do this; a policy server that is also the
inventory can. This is the authoring story that makes the weird little
syntax cheap to adopt.
