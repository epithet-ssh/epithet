# Writ policy language — session 6: C′ specified

Builds on `5.md`, which selected candidate C′ (punctuation head, keyword
tail) and left it unspecified. This session's job: make C′ implementable —
a grammar you could hand to a parser, plus the semantics decisions the
grammar depends on. Scope was deliberately the *frontend*; the IL and
evaluator questions are session 7.

## What this session settled

| # | Question | Decision |
|---|---|---|
| — | Negation scope (5.md Q2) | **Deny-only**, enforced in the grammar, and banned in macro bodies |
| — | Macro kind | **Declared keyword** — `user` / `host` / `account` |
| — | Macro composition | **Union only**; define-before-use; redefinition is an error |
| — | Rule termination | **Implicit continuation**; no `\` in the language |
| — | Head/tail boundary | **Comma**, uniform with clause separation |
| — | ttl combination (5.md Q1) | **Minimum** of all satisfied allows |
| — | notify triggers (5.md Q4) | **Registration-side `on` set**, default `["issued","denied"]` |
| — | `until` on deny | **Illegal** — allow-only |
| — | Rule labels | **Lint warning only**, never a hard error |

## Decisions and rationale

### Negation is deny-only, and the macro layer can't launder it

`!` is legal only in a `deny` head. This is a grammar-level restriction —
separate `allow-head` and `deny-head` productions — not a post-parse
check, so a negated allow is a syntax error and negation never reaches
the allow path of the IL at all.

The reason is drift, not taste. A negated matcher's set *grows* as the
IdP grows: a new SCIM group automatically matches `!$infra`, a new
`userType` automatically matches `!type:contractor`. On a deny, growth
means more restriction — a group nobody has heard of is denied the moment
it appears. On an allow, the identical mechanism grants privilege nobody
authored. The two are not one feature used in two places; one is
fail-safe under drift and the other is fail-open.

The same argument licenses negation in *all three* deny positions.
`deny $x -> !root@$prod` grows its denied account set as the host reports
new accounts; `deny $x -> *@!$dev` grows its denied host set as hosts
register. Every negation in a deny head expands what is refused.

Two consequences that make the restriction real rather than nominal:

- **Macro bodies are purely positive.** `user notinfra = !group:Infrastructure`
  is a syntax error. Otherwise a negated allow could be laundered through
  the macro layer — and in the worst form, with the `!` off-screen from
  the rule granting root. The macro layer must not express anything the
  rule layer forbids, or every rule-level restriction becomes advisory.
- **`!` prefixes the whole expression, never an atom inside a list.**
  `![$sre, $dba]` is "in neither group". `[!$sre, !$dba]` would be a
  De Morgan footgun meaning "everyone", so it is a syntax error.

Cost accepted: a carve-out is two rules. `$sre -> ubuntu@*` plus
`deny $sre -> ubuntu@$prod` where one negated allow would have done. This
is already 5.md's stated pf philosophy ("carve-outs are deny rules"); the
grammar now enforces what the style guide asked for.

### Macros declare their kind

```
user  sre   = group:SRE
host  prod  = {env=prod}
account admin = [root, postgres]
```

A macro is not text. It is a named disjunction of IL matchers of a
declared kind — the same shape as an IL `users` / `hosts` / `accounts`
field — and `$sre` in a rule is a splice, not a substitution.

Kind is declared rather than inferred, though inference would have worked
for most cases today (`group:` implies user, `{k=v}` implies host, and
only a bare word or glob is ambiguous between host-name and account-name).
Three reasons the keyword wins:

1. **Inference is a permanent constraint on grammar growth.** It bakes
   "tags are user-only, braces are host-only" into the language forever.
   Any future matcher form would have to be checked against every kind it
   might collide with. Declared kinds let forms be added freely — and
   5.md picked C′ partly for room to grow.
2. **The LSP needs it at the definition site.** 5.md's authoring story —
   hover `$prod` and see "currently matches 47 hosts" — is only computable
   if the language server knows which inventory to evaluate against
   *without* a use site. Token substitution can't answer that; a macro
   used in three places would have three answers.
3. **Errors and grep both improve.** "`$prod` is a host macro, used in
   user position" beats a parse error inside an expansion, and
   `grep '^host '` enumerates the host vocabulary.

Composition is union only. A macro may reference same-kind macros inside
a `[]` list — free, since `[]` already means union — and nothing else.
No intersection, no host-label refinement (`{$prod, role=db}` was
considered and cut as YAGNI: label selectors are shallow, so the
duplication it saves is one `env=prod`), and no tail-clause macros.

Tail macros were rejected on principle, not budget: a `$strict` standing
in for `require [oncall, approval]` moves a rule's gates off its own line,
which defeats the scan-legibility argument that selected C′ over A in the
first place. Whatever else the macro layer does, it must never hide what a
rule requires.

Define-before-use, so cycles are impossible by construction rather than by
detection, and the file reads top-down: vocabulary, then rules. This does
not dent rule order-independence — macros are fully expanded before the
evaluator sees anything. Redefinition is an error, not last-wins: silent
shadowing in a file that decides who gets root is not a feature.

### Implicit continuation; no backslashes

C′ inherited `\` continuation from pf without asking whether it was
needed. It isn't. The syntax already has two structures that are visibly
incomplete at a line break — an open `[` or `{`, and a trailing comma —
and both say "more is coming" without a dedicated sigil.

> **A rule ends at a newline, unless bracket depth is greater than zero or
> the line ends in a comma.**

The safety check is what a stray trailing comma does. The following line
would have to parse as a tail clause, but every rule begins with `deny`,
`$`, `[`, `*`, or a user tag, and none of those are clause keywords — so
the failure mode is a clean syntax error on the next line, never a silent
merge of two rules. That property comes from the head/tail split rather
than luck, and it is what makes implicit continuation safe here where it
would not be in a flat keyword grammar.

Consequence: **the head is separated from the first tail clause by a
comma**, uniform with clause separation. 5.md's double-space boundary
(`root@$prod  require [...]`) would have given a rule with no tail no
continuation signal at all. The comma also makes the head/tail boundary
explicit rather than spacing-dependent.

### ttl combines by minimum

When several satisfied allows specify different `ttl`s, the **shortest**
governs.

5.md proposed maximum, reasoning that each rule alone would have granted
its ttl, so no rule's presence should reduce what another independently
authorizes. That is a real argument for non-interference, and it loses to
a structural one: max is the single place in the language where adding a
rule *increases* privilege beyond what that rule itself grants. Everything
else composes fail-safe — deny always wins, `require` can only withhold,
unresolved facts can't unlock, evaluator errors 500 rather than fall
through. Under max, appending a broad 10m rule silently lengthens the
certs issued by a deliberately-tight 2m breakglass rule: action at a
distance in the direction of more access.

The operational objection to min is weaker than it looks, because of how
epithet uses certs. Authentication happens at connection setup and the
session outlives the cert, so a short ttl costs re-issuance latency, not
dropped sessions. Being wrong in the min direction costs latency; being
wrong in the max direction leaves an over-long credential.

Interference is the accepted cost: a narrow short-ttl rule shortens certs
for users who also match a broad rule. Both fixes are explicit — widen the
narrow rule's ttl, or make the matchers disjoint.

### notify triggers move to registration

`notify` targets are registered instances, exactly like requirement
handlers, and the registration declares which events the target wants:

```
[notify "security-alerts"]
exec   = "writ-slack"
on     = ["issued", "denied"]      # default when omitted
config = { channel = "#security-alerts" }
```

The grammar keeps `notify "security-alerts"` with no arguments. This is
the same move that settled 5.md Q3 for requirements, for the same
reasons: target identity stays trivial, the meaning of a name is defined
in one place, and "does this fire on 202s?" is answered once rather than
restated in fifty rules.

Pending (202) is excluded from the default `on` set because a 202 is
polled — firing per poll would need request-identity dedup — and the one
requirement that produces long pends, `approval`, already pages a human by
construction. A target that genuinely wants "someone tried" can opt in at
registration, and owes the dedup discussion at that point.

`notify` on a deny rule is legal; only `denied` is meaningful there, since
a deny never issues. A target whose `on` set is `["issued"]` attached to a
deny rule is dead configuration and lints as such.

### `until` is allow-only

On an allow, a failed `until` or `when` drops the rule out — less access.
On a deny, a failed condition drops the deny out — *more* access. So
conditions on deny rules are inherently privilege-increasing when false,
and each one has to earn its place.

`when` earns it: S8 (freeze) is inexpressible without it, and it is
synchronous two-state local state, which is precisely why 5.md could
prove it sound where an async `require` on a deny would fail open.

`until` on a deny does not: it is a scheduled loosening that takes effect
with no human in the loop at the moment it happens, and the same intent is
served by a flag someone must deliberately clear. Cut, re-addable later at
zero compatibility cost.

### Labels: lint only

`label` stays optional everywhere. `writ policy apply` warns when a rule
carrying `require`, `when`, or `notify` has no label, and applies it
anyway.

Considered and rejected: a hard requirement on denies and gated allows, on
the theory that those are exactly the rules whose names get read by humans
(202 messages, pages, 403 investigations) and that they are a small
minority of a large file. Rejected because an urgent apply should not
block on a naming requirement.

Mitigating the audit gap: **every compiled IL rule carries a
content-derived stable id**, so audit events always have a handle and
`label` is purely a human-readable alias. An edited rule getting a new id
is correct — it is a different rule.

## Lexical structure

**Bare words** match `[A-Za-z0-9_.*?-]+` and **may not end with `-`**.
Quotes are required for anything else and permitted everywhere.

The trailing-hyphen restriction is what makes `->` lexable without
whitespace rules: `$sre->root@$prod` munches cleanly instead of eating
`sre-` and choking on `>`. RFC 1123 already forbids hostnames ending in a
hyphen, so it costs nothing real.

**`@` is excluded from bare words**, preserving C's property that an
unquoted `@` occurs in exactly one place per rule — the head's
`account@host` separator, so the lexer needs no positional tricks.
Email-shaped identities are therefore always quoted (`id:"carol@example.com"`),
which also reinforces that writ treats identity as opaque rather than
email-semantic.

**Globs** are `*` and `?` only. No character classes — they would collide
with list `[]` — and no `**`. `*` matches any run of characters including
dots; host names are writ registrations, not DNS labels, so there is no
hierarchy for a glob to respect.

**Strings** are double-quoted with `\"` and `\\` escapes. UTF-8 passes
through literally; there are no `\u` escapes, because every string is a
SCIM attribute value, a host label, or an account name, and none of those
benefit from escape-encoded identifiers you cannot grep for.

**Timestamps** are quoted strings parsed as RFC 3339 with a mandatory
offset or `Z`: `until "2026-08-31T22:00Z"`. A policy file must not mean
different things on different machines. They are quoted because `:` is
the tag separator and admitting it to the bare-word charset would make
`group:SRE` munch as a single token; the alternative was a lexer mode
keyed on the preceding keyword, which is not worth two characters.

**Durations** are bare: integer plus `s` / `m` / `h`, composable
(`2m`, `90s`, `1h30m`). Unambiguous because they only follow `ttl`.

**Label keys** may contain `[A-Za-z0-9_./-]` bare (not ending in `-`),
accommodating k8s-style qualified keys like `topology.example.com/zone`.

**Comments** run from `#` to end of line and are not recognized inside
strings. No block comments. A comment inside a bracketed expression is
fine — the newline it ends is whitespace at depth > 0.

**Macro identifiers** match `[A-Za-z_][A-Za-z0-9_-]*`, not ending in `-`.
The ten keywords — `deny`, `user`, `host`, `account`, `require`, `when`,
`until`, `ttl`, `notify`, `label` — are reserved as macro identifiers.
They need no other reservation: keywords appear only at statement start
or immediately after a depth-0 comma, and values never occur in either
position.

## Grammar

```ebnf
file         = { item } ;
item         = macro-def | rule ;

macro-def    = "user"    ident "=" user-expr
             | "host"    ident "=" host-expr
             | "account" ident "=" acct-expr ;

rule         = allow-rule | deny-rule ;
allow-rule   = allow-head { "," allow-clause } ;
deny-rule    = "deny" deny-head { "," deny-clause } ;

allow-head   = user-expr "->" acct-expr "@" host-expr ;
deny-head    = neg-user "->" neg-acct "@" neg-host ;

neg-user     = [ "!" ] user-expr ;
neg-acct     = [ "!" ] acct-expr ;
neg-host     = [ "!" ] host-expr ;

allow-clause = "require" name-list          (* allow only *)
             | "when"    name-list
             | "until"   timestamp          (* allow only *)
             | "ttl"     duration           (* allow only *)
             | "notify"  string-list
             | "label"   string ;

deny-clause  = "when"    name-list
             | "notify"  string-list
             | "label"   string ;

user-expr    = user-atom | "[" user-atom { "," user-atom } "]" ;
user-atom    = "$" ident | user-tag ":" value | "*" ;
user-tag     = "id" | "group" | "type" | "dept" | "org" ;

acct-expr    = acct-atom | "[" acct-atom { "," acct-atom } "]" ;
acct-atom    = "$" ident | name | "*" ;

host-expr    = host-atom | "[" host-atom { "," host-atom } "]" ;
host-atom    = "$" ident | label-sel | name | "*" ;
label-sel    = "{" label-eq { "," label-eq } "}" ;      (* AND *)
label-eq     = key "=" value ;

name-list    = name | "[" name { "," name } "]" ;
string-list  = string | "[" string { "," string } "]" ;

name         = bare | string ;
value        = bare | string ;
key          = bare-key | string ;
```

The terminals `bare`, `bare-key`, `ident`, `string`, `timestamp`, and
`duration` are the lexical tokens defined in the previous section.

Notes:

- **Singleton lists may omit brackets.** `require approval` ≡
  `require [approval]`.
- **`[]` is union in match positions, conjunction in `require`.** 5.md
  recorded this asymmetry as deliberate: English carries it too ("as
  ubuntu or deploy" / "require oncall and approval") and the clause
  semantics force the right reading.
- **`{}` is always a label selector**, and multiple entries AND.
- **The file is LL(1) at statement start.** A macro-def begins with
  `user` / `host` / `account`; a rule begins with `deny`, `$`, `[`, `*`,
  or a user tag. These cannot collide, because a user matcher always
  carries a tag — no rule can begin with a bare word. This is a
  consequence of 5.md's decision that identity is opaque to writ
  (individuals are `id:"..."`, never bare usernames), and a future
  "allow bare usernames for convenience" would cost the parser property.

## Well-formedness rules

Checked after parsing, reported as errors:

1. Macro referenced before definition.
2. Macro redefined.
3. Macro kind mismatch at a reference site.
4. `!` in a macro body.
5. `!` on an atom inside a list rather than on the whole expression.
   (Grammar-enforced — listed here because the diagnostic should say
   "negation applies to the whole expression: `![$a, $b]`" rather than
   "unexpected `!`".)
6. A clause appearing more than once in a rule (use a list).
7. Unknown requirement name, unknown flag name, unknown notify target —
   resolved against writ's registries, not the grammar.
8. Duplicate key within one `{}` selector.
9. `until` timestamp already in the past at apply time.

Reported as warnings:

1. A rule carrying `require` / `when` / `notify` with no `label`.
2. A notify target whose registered `on` set makes it dead on this rule
   (e.g. `["issued"]` on a deny).
3. A macro that is defined but never referenced.
4. A `{}` selector matching no currently registered host, or a
   `group:` matching no synced SCIM group — the inventory-aware lint that
   only a policy server owning the inventory can do.

Clause order within a rule is free; the formatter canonicalizes it.

## Scenario set in final syntax

Rendered as `writ policy fmt` would emit it — note S2, S4, S6, and S8 sitting
on one line because they fit in 80 columns, while S3 and the stress test
split.

```
# ── vocabulary ──────────────────────────────────────────
user  sre   = group:SRE
user  eng   = group:Engineering
user  dba   = group:DBA
user  sec   = group:"Security Oncall"
user  infra = group:Infrastructure

host  prod       = {env=prod}
host  dev        = {env=dev}
host  staging_db = {env=staging, role=db}

# ── rules ───────────────────────────────────────────────

# S1 — baseline
$sre -> ubuntu@$prod

# S2 — elevated
$sre -> root@$prod, require [oncall, approval], label "sre-prod-root"

# S3 — authored form (the grants CLI is the preferred path)
id:"carol@example.com" -> postgres@prod-db-1,
    require approval,
    until "2026-08-31T22:00Z",
    label "carol-pgdb-incident-1234"

# S4 — attribute guard
deny type:contractor -> *@$prod, label "no-contractors-in-prod"

# S5 — dev wildcard
$eng -> *@$dev

# S6 — breakglass
$sec -> root@*, require mfa, notify "security-alerts", label "breakglass-root"

# S7 — compound selector
$dba -> postgres@$staging_db

# S8 — freeze
deny !$infra -> *@$prod, when freeze, label "prod-freeze"

# stress test — worst-case clause pileup
$sre -> root@{env=prod, role=db},
    require [oncall, approval, mfa],
    ttl 2m,
    notify "security-alerts",
    label "db-root-breakglass"

# unions, same sigil, same meaning
[$sre, $dba] -> [ubuntu, deploy]@$prod
```

## Formatter

`writ policy fmt` is normative; the LSP formats on save.

- **Macro block first**, then rules. Kind keywords and `=` aligned within
  a run of adjacent macro definitions; a blank line breaks the alignment
  group.
- **One rule per line** when it fits in 80 columns, otherwise the head on
  the first line and one clause per continuation line, indented four
  spaces.
- **Canonical clause order**: `require`, `when`, `until`, `ttl`,
  `notify`, `label`. Gates first, identity last, so scanning a column of
  rules puts the dangerous parts in consistent positions.
- **Quotes stripped** wherever the value is bare-word-legal, so quoting
  in formatted output always signals "this value contains something
  interesting". Timestamps keep their quotes (they must).
- **Singleton lists unbracketed.**
- **One space after commas** inside `[]` and `{}`; none before.
- **Comments and blank-line grouping preserved.** Blank runs collapse to
  one.
- Formatting is idempotent and never changes the compiled IL — a
  property the test suite should assert directly, since the whole point
  of a normative formatter in a security config is that reformatting is
  never a semantic diff.

## Carried forward to session 7 (the IL and evaluator)

From 5.md's list, unchanged: **Q5** dry-run, **Q6** duplicate SCIM group
displayNames, **Q8** whether to commit to a Datalog-shaped IL, **Q9**
handler packaging and a contrib set, **Q10** IL matcher taxonomy,
negation placement, schema versioning, and whether compiled IL in
`PolicyUpdated` events is authoritative or re-derivable.

New, raised by this session:

1. **Content-id derivation.** Over the compiled IL rule (so a formatting
   change or a macro rename leaves ids alone) or over source text? IL is
   the obvious answer and it interacts with Q10's "authoritative or
   derived" question.
2. **`*` in user position.** Declared legal here (`* -> ubuntu@$dev`,
   gated by `active`), but it is the only matcher that grants to
   everyone including future users, and the same drift argument that made
   negation deny-only could be pointed at it. Left legal for now because
   it is visible and intentional where `!` was neither.
3. **Grant IL and label collision.** Grants are IL-native and carry no
   label; do they get synthetic ones for 202 messages
   (`grant:carol:prod-db-1`), or does the content id serve?
4. **Requirement/flag/notify name resolution timing.** Well-formedness
   rule 7 resolves names against registries at apply time. What happens
   when a handler is later deregistered while policy still names it —
   reject the deregistration, or fail those rules closed at evaluation?
