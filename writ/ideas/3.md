# Writ architecture — session 3

Builds on `1.md` and `2.md`. Working notes.

## Cedar: explored and set aside

Investigated cedar-go in detail. ~18,400 lines non-test, well-structured
codebase. Key findings:

- Cedar's entity model supports attributes, parent hierarchies, and
  tags — richer than just entity IDs. Policies can reference
  `resource.host`, `principal.department`, etc.
- The `in` operator walks parent chains transitively, so host grouping
  via `Host::"x" in HostGroup::"production"` works naturally.
- However, **partial evaluation is experimental** (`x/exp/batch/`,
  `x/exp/eval/`). The stable public API is just `IsAuthorized()` →
  permit/deny. No residuals, no variables.
- The partial eval was the key feature for writ's obligation pattern.
  Without it being stable, Cedar's value shrinks to: a verbose policy
  language + a fast evaluator for a domain simple enough to not need one.
- If we need a DSL for authoring anyway (Cedar policies are verbose for
  SSH access), then Cedar becomes an implementation detail we might not
  need. Building a DSL *and* carrying Cedar as a dependency is worse
  than building a DSL with a simple custom evaluator.

**Decision: don't use Cedar.** Build a domain-specific policy language
inspired by pf.conf's design philosophy.

## Policy language direction: pf-inspired, not pf-copied

### Why pf is a good model

pf.conf is purpose-built for network filtering. It has exactly the
constructs its domain needs (interfaces, addresses, ports, protocols)
and nothing else. The syntax is optimized for the operator's mental
model. A writ policy language should follow the same principle: exactly
the constructs SSH access policy needs (identities, hosts, accounts,
conditions) and nothing else.

### Key patterns to take from pf

- **Macros** — named lists that expand inline. `sre = { "alice@co.com",
  "bob@co.com" }`. Simpler than entity hierarchies for most cases.
- **Tables** — for larger/dynamic sets. Host inventory maps to this.
- **Terse grammar** — reads like a sentence describing the policy.
- **Inline list expansion** — `allow host { web1, web2 }` becomes two
  rules implicitly.
- **Explicit deny** — `deny` rules for absolute prohibitions.

### Things NOT to copy from pf

- `pass` / `block` → use `allow` / `deny` (SSH access vocabulary)
- `quick` → no meaning here; evaluation model handles ordering
- `in` / `out` → no direction concept in access policy
- `on <interface>` → no interface concept
- `table ... persist` → pf-specific reload detail
- Any other pf-ism that doesn't mean something in SSH access context

The language is **inspired by** pf's design philosophy and syntax
patterns, not a transliteration.

### Sketch of the language

```
# ── Macros ──────────────────────────────────
sre = { "alice@example.com", "bob@example.com" }
prod = { "prod-web-*", "prod-db-*" }
eng = { "carol@example.com", "dave@example.com" }

# ── Tables (dynamic sets, populated at runtime) ──
table <all-hosts>     # populated by host agent
table <oncall>        # populated by oncall integration

# ── Rules ───────────────────────────────────

# absolute denial — deny rules always take priority
deny host "ca-host-1" account root

# basic access
allow user <sre> host <prod> account ubuntu

# conditional access — require obligations
allow user <sre> host <prod> account root \
    require oncall \
    require approval

# individual grant with expiry
allow user "carol@example.com" host "prod-db-1" account postgres \
    require approval \
    expire 4h

# wildcard account — any account the host reports
allow user <eng> host "dev-*" account *

# default deny is implicit (no matching allow = denied)
```

### Rule components

| Component | Required? | Meaning |
|-----------|-----------|---------|
| `allow` / `deny` | yes | permit or prohibit access |
| `user <match>` | no | identity match (default: any) |
| `host <match>` | no | host match (default: any) |
| `account <match>` | no | remote user/account match (default: any) |
| `require <name>` | no | obligation that must be satisfied (repeatable) |
| `expire <duration>` | no | grant expires after duration |

Match values can be:
- Literal string: `"alice@example.com"`
- Macro reference: `<sre>`
- Glob pattern: `"prod-*"`
- Wildcard: `*`

### Why obligations become trivial

In Cedar, obligations were hidden inside arbitrary boolean expressions,
requiring partial evaluation of an AST to discover what's unresolved.
In a pf-style language, obligations are **explicit syntactic elements**
— `require oncall` — so the evaluator trivially knows what's unresolved
without any AST reduction.

The evaluator hits a `require`, checks if that condition is met in
current state, and if not, returns it as a residual. No partial eval
machinery needed. This eliminates the main complexity that was driving
the Cedar decision.

### Requirement handlers

Each `require` name maps to a **requirement handler** in writ's code.
Handlers are not part of the policy language — they're writ's internal
mechanism:

- `require oncall` → check oncall integration (fast, inline)
- `require approval` → check for existing approval in event log; if
  none, create ApprovalRequested event, return 202 with approval URL
- `require mfa` → check for recent MFA verification

New requirement types are added to writ's code, not to the policy
language. The policy just names them.

### How the policy interacts with event sourcing

```
Policy config (static, admin-authored)
    +
Projected state (dynamic, from event log: hosts, accounts, approvals)
    ↓
Evaluator
    ↓
allow / deny / pending (202 with unmet requirements)
```

The policy file could be stored as an event (`PolicyUpdated` with full
config text) or loaded from disk. The dynamic state (which hosts exist,
which accounts, who's oncall, pending approvals) lives in the event log
projections.

## Evaluation semantics

### Proposed (needs further discussion)

- `deny` rules evaluated first — if any match, denied (403). Denials
  are absolute and cannot be overridden by allow rules.
- First matching `allow` rule wins.
- If no allow rule matches, denied (403).
- If the matching allow rule has `require` clauses, each is checked.
  All satisfied → permit. Any unsatisfied → 202 pending.
- Default deny is implicit.

### Open questions on evaluation

- First-match vs. last-match vs. priority-based ordering?
- Should deny always win, or can allow override deny in some cases?
- How does rule ordering interact with macros and tables that change
  dynamically?
